<h1 class="font-display text-3xl text-white mb-2">Introduction</h1>
<p class="text-[#a89dc7] mb-8">Build plugins for TitanClient with native C++, QuickJS/TypeScript, or Java.</p>
<div class="docs-content prose prose-invert max-w-none">
<h2 id="what-is-titanclient">What is TitanClient?</h2>

<p>
TitanClient is a native OSRS client built around a controller process and an injected game-client runtime.
Plugins extend the client with overlays, panels, automation helpers, game-state readers, cache lookups,
and developer tools through a stable SDK surface.
</p>

<p>
The public SDK is shared across the supported plugin authoring surfaces. C++, QuickJS/TypeScript, and Java
all reach the same core game-state model: live entity handles, state facades, utility helpers, generated
gamevals, events, overlays, and controller side panels.
</p>

<h2 id="sdk-architecture">SDK Architecture</h2>

<p>
The SDK is organised into four orthogonal groups of entry points. New public symbols should fit one of
these shapes so each language can expose the same concept naturally.
</p>

<table>
<thead>
<tr>
<th>Shape</th>
<th>C++ Namespace</th>
<th>TS Namespace</th>
<th>Java Package</th>
<th>What it is</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Queries</strong></td>
<td><code>titan::queries::*</code></td>
<td><code>titan.queries.*</code></td>
<td><code>net.titan.api.queries</code></td>
<td>Chainable, filterable views over live game collections.</td>
</tr>
<tr>
<td><strong>State</strong></td>
<td><code>titan::state::*</code></td>
<td><code>titan.state.*</code></td>
<td><code>net.titan.api.Client</code> and services</td>
<td>Facades that read or manipulate a specific subsystem.</td>
</tr>
<tr>
<td><strong>Utils</strong></td>
<td><code>titan::utils::*</code></td>
<td><code>titan.utils.*</code></td>
<td><code>net.titan.api.utils</code></td>
<td>Composition helpers built over queries and state.</td>
</tr>
<tr>
<td><strong>Gamevals</strong></td>
<td><code>titan::gamevals::*</code></td>
<td><code>titan.gamevals.*</code></td>
<td><code>net.titan.gamevals</code></td>
<td>Generated native gameval constants and metadata lookups.</td>
</tr>
</tbody>
</table>

<p>
Free helpers that are not subsystem facades stay at the top level:
<code>titan::log</code>, <code>titan::logf</code>, <code>titan::addChatMessage</code>,
<code>titan::runOnClientTick</code>, <code>titan::runOnRender</code>, registration macros,
and <code>titan::Plugin</code> itself.
</p>

<h2 id="sdk-versioning">SDK Versioning</h2>

<p>
The current public SDK version is tracked in <code>shared/titan/detail/abi.h</code>.
</p>

<table>
<thead>
<tr>
<th>Constant</th>
<th>Current Value</th>
<th>Meaning</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>kSdkVersion</code></td>
<td>107</td>
<td>The latest SDK version exposed by this build.</td>
</tr>
<tr>
<td><code>kMinSupportedSdkVersion</code></td>
<td>107</td>
<td>The oldest native SDK version this build will load.</td>
</tr>
</tbody>
</table>

<div class="callout callout-info">
<p>
<strong>Native rebuild required:</strong> the current compatibility floor equals the current SDK
version. Native plugins must advertise <code>sdkVersion = 107</code>; rebuild older DLLs against
the current public headers. QuickJS and Java plugins use their runtime bridges rather than the
native ABI version gate.
</p>
</div>

<h2 id="current-highlights">Current SDK Highlights</h2>

<ul>
<li>SDK v107 exposes runtime item submenu labels through <code>subOps</code> and sets the native compatibility floor to 107.</li>
<li>SDK v105 makes tile-object, ground-item, and widget handles live across ticks; use <code>exists()</code> and <code>snapshot()</code> explicitly.</li>
<li>SDK v102 adds idempotent prayer helpers; SDK v97 adds cross-runtime Break Handler participation and account-profile services.</li>
<li>SDK v96&ndash;104 expands panels with containers, alignment, tabs, dropdowns, disabled scopes, help markers, and badges.</li>
<li>SDK v100&ndash;101 expands WorldArea, NPC, inventory, object, and widget query filters.</li>
</ul>

<h2 id="plugin-loading">Plugin Loading</h2>

<p>
Local disk plugin discovery is intended for developer workflows. In Release builds, both <code>--dev-mode</code>
and the <code>feature.debug_mode</code> entitlement are required before local <code>.dll</code>,
<code>.js</code>, or <code>.jar</code> files are discovered. Debug/source workflows use the same local
scan model once the runtime is launched in DEV mode.
</p>

<p>
Published plugins are delivered to users through the controller and client delivery pipeline. Local disk
scan paths are still useful for plugin development, template projects, dev sessions, and manual testing.
</p>
