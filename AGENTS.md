# Stark Mercher Bot — Strict Rules

For shared performance rules (native handle exhaustion, caching patterns,
per-frame/per-tick discipline, click safety), read
`~/.codeium/windsurf/memories/titan-performance-rules.md`.
For shared SDK/login/humanisation reference, read
`~/.codeium/windsurf/memories/titan-sdk-shared-reference.md`.

## Mercher-specific performance details

The following are mercher-specific implementation details that build on top of
the shared performance rules. The shared rules are not repeated here.

### Cached settings (mercher-specific list)

The mercher caches these settings in plain JS fields on the plugin class,
initialized in `onEnable()` and refreshed in `onSettingChanged()`:

- `autoMode.value` → `autoModeValue` (per-frame: `onMainLoop`, overlay; per-tick: `autoLoopTick`, `breakStep`, `hopStep`)
- `showHud.value` → `showHudValue` (per-frame: overlay render callback)
- `hopWorlds.value` → `hopWorldsValue` (per-tick: `hopStep`)
- `idleActivity.value` → `idleActivityValue` (per-tick: up to 11 reads per tick)
- `doNotSleep.value` → `doNotSleepValue` (per-tick: `breakStep`, `isNightlyBreakDue`, etc.)
- `logInfo.value` → `logInfoValue` (per-tick: `humanLog`, `infoLog`, inline checks)
- `logDebug.value` → `logDebugValue` (per-tick: `debugLog`, inline checks)

### isMembersWorld() — world-ID-aware cache

`titan.state.world.metadata()` returns a full snapshot of the world list (~100+ `WorldMetadata` native objects) on every call. `isMembersWorld()` is called multiple times per tick via `offerSlotCount()` and `auditGeState()`. The cache is **world-ID-aware** in `grand_exchange/widgets.ts`: it caches both the boolean result AND the world ID it was computed for. On each call, `titan.state.world.current()` (scalar read, no native handle) is compared to the cached world ID — if they match, the cached boolean is returned without any native handle creation. `metadata()` is only re-fetched when the world ID actually changes (after a hop or login to a different world). With 5 accounts (~6 cycles/hour), this eliminates ~600+ native handles/hour when the world hasn't changed.

### Entity query cache — GE clerks, GE booths, logout door, world list

GE clerks (NPCs), GE booths (scenery objects), and the logout door (scenery object) are **static** — cached at module level (single `toArray()`/`nearest()` call per session):
- `grand_exchange/clerk.ts` — `cachedClerks` / `cachedBooths` arrays, invalidated via `invalidateEntityQueryCache()`. Both queries use `.currentWorldView()` to scope to the active WorldView (unscoped queries can span multiple loaded WorldViews with stale/ghost copies).
- `antiban/logout.ts` — `cachedLogoutDoor`, scoped via `.currentWorldView()` (was previously unscoped — scanned ALL loaded objects every logout cycle).
- `antiban/hopper.ts` — `cachedWorldList` array, invalidated via `invalidateWorldListCache()`.

All invalidated on: (1) hop completion, (2) login state change, (3) tick counter reset, (4) `onDisable`.

### Title widget cache — findByText is a full widget scan

`findTitleWidget()` caches the title widget `WidgetState` handle at module level. Once found, the handle is reused — `exists`/`visible` are fast property reads on a live handle. When the widget disappears, `exists` returns false and the cache self-invalidates. A 5-second throttle (`TITLE_WIDGET_MISS_THROTTLE_MS`) prevents back-to-back full scans while the login screen loads. `logout.ts` `tryClickText` tries `find()` first, `findByText` as fallback only.

### idle-activity modules — use cross-tick inventory snapshot

`idle-activity/chocolate-dust.ts`, `idle-activity/ultra-compost.ts`, and `idle-activity/goat-horn.ts` read from the cross-tick inventory snapshot (`getInvSnapshot()`) instead of calling `getAll()` directly. Without this, `hasIdleActivityItems(bot)` created ~84 native handles per tick during idle monitoring, accumulating ~900k handles over ~1h48m.

### idle-activity processing phase — periodic cache invalidation

All three idle activities call `invalidateInvCache()` every `PROCESSING_CACHE_REFRESH_TICKS` (15 ticks ≈ 9s) during the `SUB_CONV_PROCESSING` sub-step, keeping the snapshot fresh enough to detect completion without exhausting handles.

### wallClockStep — login snapshot throttle

`titan.state.login.snapshot()` inside the logged-out `wallClockStep` block is throttled to once per 10 seconds (`LOGIN_SNAPSHOT_TTL_MS`) — account detection at the login screen does not need sub-second latency. `loginStep()` itself is throttled to ~3 ticks (`LOGIN_STEP_MIN_INTERVAL_MS`).

### Click-jitter generation counter — stale callback guard

`clickWithJitter`/`sendKeyWithJitter` use a module-level generation counter (`clickJitterGeneration`) incremented by `resetClickJitter()` on `onDisable`. Pending callbacks bail early if the generation doesn't match — preventing stale native handle creation from dead plugin instances.

### Dead-instance guards — `terminated` + `enabled` + `instanceId`

`onDisable` sets `terminated = true` and `enabled = false` as its first statements. Every event handler (`onGameTick`, `onMainLoop`, `onGameStateChanged`, `onChatMessage`, `onMenuOptionClicked`, `onSettingChanged`) bails on `if (this.terminated) return;` — if the runtime keeps stale registrations firing after hot reload/toggle, dead instances do zero work instead of running full tick logic multiplied by instance count. The overlay render callback bails on `!isHudActive` (cleared in `onDisable`).

`enabled` is a separate flag (true only between `onEnable` and `onDisable`) guarding all 7 `buttonSetting` onClick handlers. `terminated` alone is insufficient there: `startStop`'s resume path calls `resetForResume()` which clears `terminated` — a dead instance's `onClick` would resurrect it. A dead instance's `enabled` stays false permanently because `onEnable` never runs on it again. The guards also prevent dead instances from writing shared hidden settings (`saveBreakState`, offer cache) which would corrupt the live instance's persisted state.

`instanceId` is a random 4-char field stamped per `new StarkMercher()`, logged on `onEnable` and in the 30s `onMainLoop` diag (`diag: instance=xxxx clientTick=N`). Multiple instanceIds logging the same clientTick confirms stale registrations are firing.

## User build preference

- Do **not** run `npm run build`, `npm run watch`, or any other build/compilation command unless the user explicitly asks. The user will build the plugin manually when they are ready.
- `npm run typecheck` runs `tsc --noEmit`. The codebase has pre-existing type errors; new errors introduced by a change must be fixed.
- Standard verification after code changes: `npm run typecheck`, `npm run state-guard`, `npm run test:scenarios`, `npm run test:integration`. Do not run these unless explicitly asked.

The volume fields (`buyVolume`, `sellVolume`) are used by `reconstructEntry` to compute approximate ETAs for priceHistory-only items. `getPriceHistoryEntryById` resolves truncated GE slot names (e.g. "Antidote++..." → itemId 5952 → "Antidote++(4)") by looking up the slot's itemId — the JSON is keyed by item ID (string), so the id→entry map is built alongside the name→entry map in the same pass. - `data/offer-cache.ts` — `OfferCacheManager` wrapping the persisted cache with price revision logic (10% of gross profit, min 1 gp, never below the tax-break-even floor pre-abandon, **thin-margin items (< 10gp gross margin) use the same revision schedule** — the margin floors the reduction to 1gp anyway, so a separate aggressive schedule is redundant, floor-hit markers that advance the revision count when the price is already at the floor so floor-stuck items can reach the abandon/final-dump thresholds, **margin-aware early abandon** via `floorHitCount` to free slots sooner instead of cycling at the same floor price for ~50+ minutes — thin-margin items (< 10gp gross margin, e.g. Revenant ether) abandon after 4 consecutive floor-hits since abandoning bulk items is very costly; thick-margin items (>= 10gp) abandon after 2 floor-hits since the slot is worth more than waiting), `isAtDumpFloor` (returns true when sell price <= tax-break-even floor AND revision count >= final dump threshold — used by `isSellOfferStale`'s dump-floor guard which checks a hold timer before skipping stale checks: 90 min for rev 8, 30 min for rev 9+; after the hold timer expires with 0% progress, the controlled loss dump fires, pricing below the tax-break-even floor at rev 9-12 to free stuck slots), `isDumpFloorStuck` (checks hold timer + 0% progress at dump floor), `canReduceControlledLoss` (returns false when rev >= 9 and sell price is at the 80% of buyPrice minimum — offer is left to fill at its own pace), `reconstructEntry` (reverse reconciliation from live GE slots after cache loss — parses the GE slot's `priceText` for the actual offer price, computes ETAs via `computeRuntimeEtas` for merchableItems.json items, or via the same non-linear ETA model with `BASE_FILL_TIME_MIN` + 50% market share + 15% volume buffer for priceHistory-only items, marks entries with `reconstructed: true` for the zero/low-profit abort guard and `reconstructedBuyPrice: true` for phantom loss skipping), `fixModeMismatch` (corrects cache entries whose mode doesn't match the live GE slot type after a hidden setting revert from plugin reloads — uses the GE slot's `priceText` as the actual price, applies the value-aware sell ETA cap, preserves buy-limit tracking), `confirmSellOffer` (marks sell confirmed + resets `offerPlacedAt` to the actual placement time), `markDirty`/`getAccountName` (for cross-account cache refresh), and Wiki API stub. `fetchWikiPrice` (stub — URL not yet configured). All `Cache:` logs are gated by `logInfo` (offer recording, revisions, reconstruction, dumps, abandons, buy-limit, removals) or `logDebug` (per-fill qty tracking, floor-hit markers, "already at floor" checks, "no expired entries" cleanup). The "Wiki API URL not configured" error remains unconditional.
- `data/daily-profit.ts` — per-account daily profit tracking. `addDailyProfit`, `getDailyProfit`, `resetDailyProfit`, `getDayStartMs`. Persisted in a hidden JSON setting. Includes duplicate account-key migration on load: keys equivalent under whitespace + casing normalization (replaces all whitespace chars including non-breaking spaces U+00A0 with regular space, collapses multiples, trims, lowercases — catches "hc\u00A0fruitz" vs "hc fruitz" which look identical but are different JSON keys) are merged (same-day profits summed, most recent day wins across different days) under a canonical key (roster match preferred, else first-seen raw key), with a normalized-lookup fallback in `getDailyProfit`/`addDailyProfit` for defensive casing tolerance. Write paths use the existing canonical key to prevent re-creating duplicates. Resets at UK midnight via day-rollover comparison on read/write. Used by the auto-loop for merch-history/loss accounting (not displayed on the overlay — the previous `bot.cachedDailyProfit` HUD field was removed because it froze the bot at runtime).
- `widgets/bot-overlay.ts` — minimal HUD overlay. `renderBotOverlay` draws one rect + two text lines: the current autoMode label (Paused / Normal / Slow / F2P) from `bot.overlayStatusText`, and a "Start: HH:MM" line from `bot.sessionStartUKTime` (both plain-JS fields updated only in `onEnable` / `onDisable` / `onSettingChanged`). The render callback does zero allocations, zero `Date.now()`, zero native SDK reads, zero cache lookups. Registered via `this.overlay({ layer: 'AboveWidgets' })` in `stark-mercher.ts`. - `antiban/humanised-delay.ts` — `DelayProfile`, `generateDelayProfile`, `setDelayProfileForAccount`, `createDelay`, `setDayBounds`, `getFatiguePercent`; per-account deterministic humanised delay function inspired by mixology's anti-ban layers (jitter, hesitation, outlier, jitter amplification, micro-distraction, rare distraction). The `suppressDistractions` parameter (4th arg) skips the micro-distraction and rare-distraction layers — used by GE offer flows (buy/sell/abort) for mid-flow steps where a 6-60s pause between connected clicks is non-human. Includes a **diurnal pace multiplier** (fatigue) that drifts smoothly across the waking day: 0.8x (20% faster) at 0% fatigue after nightly sleep, linearly to 1.05x (5% slower) at 100% fatigue before the next nightly sleep. Applied to the final delay after all layers. Day bounds are set by `setDayBounds()` from `markNightlyBreakFinished`, `scheduleNextNightlyBreak`, and `restoreBreakState`. `getFatiguePercent()` returns the current 0-100 fatigue (no longer displayed on the overlay — the diurnal pace multiplier is still applied internally by `createDelay`).
- `antiban/hopper.ts` — `hopStep`, `completeHop`, `onChatMessage`, `saveHopState`, `invalidateWorldListCache`. World hop state machine adapted from mixology. Picks a random safe world matching the current mode (members world for Normal/Slow, F2P world for F2P mode) on a **bimodal/burst interval** (70% normal 15–60 min, 20% burst 2–8 min, 10% long 60–150 min). After a burst hop, the next interval has a 50% chance of also being a burst, simulating the human pattern of hopping 2–3 times in quick succession. The hop timer is global (not per-account), shared across account rotations, and persisted to the hidden `hopState` setting so script reloads don't reset the schedule. Pauses auto-loop during hop and for a short resume delay after. `titan.state.world.list()` result is cached at module level (`cachedWorldList`) — the world list only changes on hop/login transitions, so `pickWorld` reads from the cached list instead of re-fetching on every hop attempt.
- `antiban/session.ts` — break/sleep state machine + hop safe-boundary functions. `breakStep` (checks `titan.state.login.isLoggedIn` first — a scalar read that does not create a native handle — to avoid per-tick native handle creation during normal merching; the logged-out branch uses `bot.currentPlayerName` for break/rotation logic, NOT `localPlayer?.name`), `wallClockStep` (1-second throttled via `bot.lastWallClockMs` — see "wallClockStep — 1-second throttle" section above), `resetBreakState`, `initSessionProfile`, `markNightlyBreakFinished`, `formatUKTime`, `getSafeBoundaryReason`, `isAtSafeBoundary`, `shouldPauseForHopBoundary` (returns false when any GE flow is active — blocking an active flow mid-step would deadlock the hop boundary: the flow can't advance, and the hop can't fire because `isAtSafeBoundary` sees the active flow), `resetHop`, `forceHop`, `resetHopState`, `loadHopState`. Integrates multi-character rotation: on logout, `tryImmediateRotation()` checks if a different account is eligible immediately; during the break wait, `wallClockStep` periodically (every 10s) re-checks for a newly-eligible account; on break end, calls `selectNextAccount()` to pick the account whose break ends soonest (with longest-since-login tiebreaker). `initSessionProfile` is the single source-of-truth read of `titan.state.client.localPlayer?.name` — it sets `bot.currentPlayerName` (canonicalized to the roster's version when the game name matches under whitespace + case normalization via `normalizeAccountName` in account-rotation.ts, which collapses non-breaking spaces U+00A0 and other Unicode whitespace — the OSRS client's `localPlayer.name` for "hc fruitz" is often "hc\u00A0fruitz", which without normalization would fail to match the roster entry). This prevents duplicate merch history keys that fragment profit tracking and cause the profit UI to show the same account twice, and ensures `bot.currentPlayerName` always holds the roster-canonical name so `tryImmediateRotation`'s same-account guard, `selectNextAccount`'s break-state lookup, and the unexpected-logout roster check all work correctly. All same-account comparisons in the rotation paths (`tryImmediateRotation`, the break-ended rotation, the unexpected-logout rotation) use `normalizeAccountName` defensively. **Nightly schedule persistence**: `saveBreakState(bot)` persists the bedtime/wake schedule to the hidden `breakState` setting. `clearBreakState(bot)` (called when a break ends and the bot is in-world) preserves the nightly schedule by saving a minimal state with `breakPhase='none'` and the schedule fields — it does NOT wipe to `'{}'`. `wipeBreakStateSetting()` (private) is used only for true wipe cases (fully-passed nightly sleep, parse error). `restoreBreakState(bot)` restores the schedule on hot reload; if a short-break target has passed, it preserves the nightly schedule and transitions to `logging_in` instead of discarding everything.
- `antiban/account-rotation.ts` — multi-character roster management. `getRoster`, `isRotationEnabled`, `normalizeAccountName` (whitespace + case normalization — collapses non-breaking spaces U+00A0 and other Unicode whitespace to a single regular space, trims, lowercases; mirrors `normalizeAccountKey` in data/daily-profit.ts; used by `initSessionProfile` canonicalization and all rotation same-account comparisons so a game name like "hc\u00A0fruitz" matches the roster entry "hc fruitz"), `selectNextAccount`, `isRotationDueForLoggedIn` (returns a different eligible account's name if rotation should trigger while the current account is logged in — used by the auto-loop's idle-activity dispatch to yield the idle activity when another account becomes eligible), `getSoonestBreakEndMs`, `getNextAccountName`, `recordAccountLogout` (enforces a 10-minute minimum re-login floor via `MIN_ACCOUNT_BREAK_MS`, exempt for hour-pause via `enforceMinBreak=false`), `recordAccountLogin`, `loadRotationIndex`, `saveRotationIndex`, `isAccountSleeping`, per-account break state cache (`getAccountBreakState`/`saveAccountBreakState`/`clearAccountBreakState`). When the roster has 2+ names, the bot rotates between accounts: each runs the full auto-merch loop until idle, logs out, and the next eligible account (awake + break lapsed) logs in. Selection is time-based — the account whose break ends soonest is selected, with the longest-since-login tiebreaker preventing starvation. When the roster is empty or a single name, the bot behaves as a single-account bot.
- `input/typing.ts` — `humanType`, `isTyping`, `cancelTyping`, `setTypingProfile`, `setTypingProfileForAccount`; humanised keyboard typing with per-character delays. `isTyping()` also returns true while a typing-mistake correction sequence is active, and advances the tick-driven mistake state machine once per game tick via `tickMistakeSequence()`.
- `input/typing-profile.ts` — `TypingProfile` (`baselineMs`, `jitterMs`), deterministic per-account profile generation via djb2 hash + mulberry32 PRNG.
- `input/typing-mistakes.ts` — `TypingMistakeProfile` (`nameMistakeChance`, `quantityMistakeChance`, `priceMistakeChance`), `typeStringWithMistake`, `setTypingMistakeProfileForAccount`, `cancelTypingMistakeSequence`, `tickMistakeSequence`; occasional wrong-character + backspace correction during GE typing. The mistake sequence is driven by a **tick-based state machine** (not `setTimeout` — the Titan runtime does not expose `setTimeout`, so any use crashes the plugin with `ReferenceError`). `tickMistakeSequence()` is called from `isTyping()` in `typing.ts` every tick, advancing gap countdowns (realisation delay, post-backspace gap) using `titan.state.client.tick` for dedup. Phases: `phase1_typing` → `realise_gap` (count down N ticks) → `post_backspace_gap` (1 tick, Backspace on entry) → `phase2_typing` → done. A tick-based safety watchdog (`MAX_MISTAKE_DURATION_TICKS = 14` ≈ 8.4s) force-clears a stuck sequence. `BuyOfferFlow` and `SellOfferFlow` also call `cancelTypingMistakeSequence()` in `waitTick()` (on re-attempt) and `fail()` to prevent a stuck sequence from poisoning subsequent typing operations.
- `grand_exchange/buy-offer.ts` — `BuyOfferFlow` multi-tick state machine for placing a buy offer from start to finish (21 steps). **Early-stop search typing**: while typing the item name (step 4), the flow checks each tick whether the desired item has appeared as the **unique** GE search result via `scanSearchResultsUnique` (e.g. "magp" uniquely matches "Magpie impling jar"). If so, the remaining typing is cancelled via `cancelTyping()` — real players stop typing once they see their item. A minimum prefix of 3 characters is required. The check is naturally safe during typing-mistake sequences (the wrong character won't produce an exact match). After spotting the unique result, there's a 40% chance of a 1-2 tick "looking at results" delay before clicking, simulating the human moment of registering the result before acting. **Stateless recovery**: No longer used at runtime — `runStartupAudit()` in `stark-mercher.ts` now sends a one-time Escape to close any open GE sub-screen on script start, and the auto-loop starts fresh flows. The `resumeFromState(audit)` method remains in the class but is not called. **Confirm-grace isolation**: `waitForConfirm()` (step 19) uses a single `waitTicks` counter both for polling `isOfferConfigOpen()` (waiting for the config screen to close) and for the subsequent slot-occupied verification. When the config screen takes 3+ ticks to close, the counter is exhausted before slot verification begins, causing false `Offer was not placed — slot is still empty after confirm` failures even when the offer appears on the next tick. The fix resets `waitTicks = 0` the first time `isOfferConfigOpen()` returns false, giving the slot-occupied check its own independent 3-tick grace window.
- `grand_exchange/sell-offer.ts` — `SellOfferFlow` multi-tick state machine for placing a sell offer (17 steps).
- `grand_exchange/abort-offer.ts` — `AbortOfferFlow` multi-tick state machine for aborting an offer and collecting (9 steps).
- `grand_exchange/auto-loop.ts` — automated merching loop state machine. `autoLoopTick`, `createAutoLoopState`, `resetAutoLoop`, `AutoLoopState`, `AutoLoopPhase`. Loop order: GE-open check → collect → stale offers → sell → buy. **Startup**: `runStartupAudit()` in `stark-mercher.ts` handles the first-tick audit. If a GE sub-screen is open (offer config / search / quantity / price prompt), it sends a one-time Escape to close it — the auto-loop then reopens the GE and starts fresh flows. No flow reconstruction is attempted. **Cache reconciliation 'unknown' slot guard**: both forward reconciliation (Step 2b — removes orphaned cache entries) and reverse reconstruction (Step 2c — reconstructs missing cache entries from live GE slots) defer to the next tick if any slot has `type === 'unknown'` (GE widget not fully loaded). Without this guard, unknown slots have null `itemName`, so forward reconciliation incorrectly removes active cache entries as orphaned; reverse reconstruction then restores them with potentially different sell prices from the refreshed merchableItems.json, causing profit loss. Both flags (`cacheReconciled`, `cacheReconstructed`) are only set to `true` when all slots are readable, and are reset to `false` by `resetInFlightActionState()` on hop/break/login transitions. **Idle diagnostic throttle**: when the bot is continuously idle (nothing to do), the "no action" diagnostic logs (GE slots summary, stale check, sell/buy scan, fallback-selection logs — frozen non-lowball/lowball fallback, lowball tier selection, partial-quantity fallback, and the MIN_BUY_OFFER_VALUE skip, and ETA) are throttled to every ~5 seconds (`IDLE_DIAG_INTERVAL_TICKS = 8` ticks) via `bot.lastIdleDiagTick` instead of every tick (~600ms), preventing hundreds of redundant log lines during idle periods. The fallback-selection logs spam when a lowball/partial item is found by the scan but then skipped by the `MIN_BUY_OFFER_VALUE` (100k GP) floor — without the throttle, the "using lowball item Astral rune..." line repeats every tick. Action-triggering logs (aborting, selling, buying, collecting) always log regardless. `lastIdleDiagTick` is reset in `resetInFlightActionState()` and the disconnect cleanup so the first idle tick after an action or login always logs.
- `grand_exchange/actions.ts` — GE click, typing, Enter, quantity, price, confirmation helpers. `clickWidget` per-click trace logging is gated by `logDebug` via a module-level `setClickWidgetDebugLog` setter (wired up from `auto-loop.ts`); the "widget not found" error log remains unconditional.

## Humanisation / anti-ban

- **Always keep humanisation / anti-ban in mind** for all changes (timings, fatigue, breaks, micro-AFKs, mistakes, etc.).
- The `createDelay(base, triggerChance, max?, suppressDistractions?)` function in `antiban/humanised-delay.ts` is the single entry point for humanised delays. Use it between any actions in the flow. `base` is clamped to minimum 1. `triggerChance` (0-100) is the % chance the humanisation layers fire on top of the base. `suppressDistractions` (default `false`) skips the micro-distraction and rare-distraction layers — pass `true` for mid-flow steps in connected click sequences (buy/sell/abort offer flows) where a 6-60s pause is non-human. After all layers fire, the final delay is scaled by a **diurnal pace multiplier** (fatigue): 0.8x at 0% fatigue (just woke up) drifting linearly to 1.05x at 100% fatigue (about to sleep). Day bounds are managed by `setDayBounds()` in `session.ts` — reset on `resetBreakState`, set on nightly wake (`markNightlyBreakFinished`), updated on schedule recompute (`scheduleNextNightlyBreak`), and restored on hot reload (`restoreBreakState`). Short breaks do NOT reset fatigue — only nightly sleep does.
- The `DelayProfile` is deterministic per account name (same djb2/mulberry32 pattern as `typing-profile.ts`). Generate it via `setDelayProfileForAccount(playerName)` at startup.
- Humanisation layers (inspired by mixology): reaction bias, jitter, hesitation multiplier, delay outlier (with nested outlier), jitter amplification. These fire only when the trigger chance succeeds. Two additional layers fire independently of `triggerChance` and bypass the `max` cap: **micro-distraction** (2-4% chance, +10-40 ticks / 6-24s, "glanced at chat/wiki") and **rare distraction** (0.1% chance, +30-100 ticks / 18-60s, "tabbed out"). Together these create a visible long tail in the reaction-time distribution so the bot doesn't always react within 1-8 ticks. Both are skipped when `suppressDistractions` is `true` — the GE offer flows (buy/sell/abort) pass this for all their internal `computeDelay` calls, so the distraction tail only fires between independent actions (idle, walk, open GE) and during the post-Confirm/post-Collect thinking pauses where a human would actually glance at chat or tab out. Connected click steps within flows use `computeDelay(1, 25, 4)` (1 tick base, 25% hesitation, max 4 ticks — 75% rapid burst within 1-3 ticks, 25% normal pace 2-4 ticks). After each flow completes (buy/sell/abort) and after the auto-loop's collect, a **thinking pause** of `createDelay(5, 50, 20)` is set (50% ~3-5 ticks ≈ 1.8-3s "glanced at result", 50% ~10 ticks ≈ 6s "reading the result", rare outlier up to 20 ticks ≈ 12s) — matches human data showing 3-8s typical pauses after Confirm/Collect with rare 8-15s outliers.
- The `humanType()` function in `input/typing.ts` already uses profile-derived per-character timing. The GE buy/sell flows use `typeString()` (in `grand_exchange/actions.ts`) which routes through `typeStringWithMistake()` in `input/typing-mistakes.ts`. This wraps `humanType()` with a small per-type chance of a wrong-character + backspace correction: the bot types part of the text, inserts a wrong character (a random letter for item names, a random digit for quantities/prices), waits a humanised realisation delay via `createDelay(2, 100, 3, true)` (1-3 ticks / 0.6-1.8s, distractions suppressed — mid-flow), presses Backspace, waits 1 tick, then types the remainder. The mistake chances are deterministic per account (`TypingMistakeProfile` via djb2/mulberry32): `nameMistakeChance`, `quantityMistakeChance`, and `priceMistakeChance` are each independently sampled in 0.3-1.0%, so a full buy offer flow (name + quantity + price) has roughly a 0.9-3.0% chance of at least one visible mistake. The mistake is always corrected before the flow's validation step, so the final typed text is always correct. `isTyping()` returns true for the entire sequence (including the realisation gap) so the flow's `waitForTyping` step doesn't advance prematurely. The mistake sequence is driven by a **tick-based state machine** (not `setTimeout` — the Titan runtime does not expose `setTimeout`), advanced once per game tick via `tickMistakeSequence()` called from `isTyping()`. A tick-based safety watchdog (`MAX_MISTAKE_DURATION_TICKS = 14` ≈ 8.4s) force-clears a stuck sequence, and `BuyOfferFlow`/`SellOfferFlow` call `cancelTypingMistakeSequence()` on re-attempt and failure to prevent a stuck sequence from blocking subsequent typing.
- Whenever a new humanisation / anti-ban profile setting is added, also add it to any profile summary logger so it is visible.

## Client tick reset after disconnect/relogin/world hop

When the client disconnects and logs back in — whether from a raw disconnect, a world hop that involved a logout/login cycle, or any other reconnection — the client tick counter (`titan.state.client.tick`) can reset to a smaller value. All tick-based state becomes stale: `actionStartTime` is ahead of the current tick, making `ticksSinceAction = tick - actionStartTime` negative. Since `canPerformAction()` checks `ticksSinceAction >= actionDelay`, a negative value can never satisfy this, so the bot locks forever.

- `canPerformAction()` in `general/timing.ts` has a defensive check: if `ticksSinceAction < 0`, it resets action state and returns `true`.
- `onGameTick` in `stark-mercher.ts` also detects `lastActionTick > tick` and resets stale action state.
- Any new tick-based state field must handle a backwards tick counter reset.

## State-change bug-prevention rules

These rules exist because the most common bugs are state values that outlive the event that set them.

### 1. State lifecycle map before editing

For any `bot.*` field that is added or touched, state the following in a **state impact note** before committing:
- Field name
- What sets it
- What clears it (exact success, failure, login, `onEnable`, `resetInFlightActionState`, or the handler that ends the action)
- Which files were changed

### 2. Reset checklist

Every new transient state must be reset in **all** of these places unless there is an explicit reason not to:
1. `onEnable()`
2. `resetInFlightActionState()` (break/hop/world transition — clears auto-loop flows, test flows, idle-for-break flags, cache reconciliation flags, and action throttle)
3. The handler that naturally ends the action (e.g. flow completion, flow failure)
4. The login/settle path if it relates to breaks or post-login UI

### 3. Defensive invariants in `tickLogic`

`sanityCheckState(bot, tick)` is called at the top of `tickLogic()`. It auto-corrects cheap stale state — clearing stale `abortSlotInfo` when no abort flow is active, resetting `phase` to `'idle'` when the corresponding flow is gone, and clearing stale `logoutComplete` when not in a break. New stale-state fixes go here; they must be logged.

### 4. Trace-first for state changes

When adding or changing state, add a `debugLog`/`humanLog` at the set and the reset. Do not rely on silence to mean success. The `logDebug` UI toggle controls whether debug logs are printed; the `logInfo` UI toggle controls whether info-level logs (rotation, breaks, login/logout, hops, offer lifecycle) are printed.

## Break and hop safe boundaries

A hop is blocked by either player activity, an active GE flow, or the post-login settle period. `getSafeBoundaryReason()` checks, in order:
1. `bot.hopInProgress` — a world hop is already in flight.
2. **Post-login settle** — `bot.postLoginResumeAtMs > 0`. The client is still rendering the world / clearing promo widgets after login. `tickLogic` runs `hopStep` before the `postLoginResumeAtMs` gate, so without this check the hop is dispatched while the client is still settling, gets rejected by the world switcher with "busy action", and the native `hopIngame()` sequence continues to spam Logout/World Switcher clicks that interfere with the auto-loop.
3. `!isPlayerIdle(bot)` — the player is animating or moving.
4. **Idle buffer** — player has been idle for less than 2 ticks.
5. **GE flow completion gate** — `bot.autoLoop.activeBuyFlow`, `activeSellFlow`, or `activeAbortFlow` is non-null. A flow can sit in a between-clicks wait where the player is visually stationary, but the world switcher still rejects the hop with a "busy action" message because the flow owns the interaction state. The flow fields are only cleared once the flow's state machine returns `done`/`failed` and the auto-loop transitions back to `idle`, so checking them here is the authoritative signal that the GE is quiescent.
6. **Auto-loop phase** — `bot.autoLoop.phase` is anything other than `idle` or `waiting`. `waiting` (all slots occupied, nothing to do) is safe because no flow is active and the loop is settled; `opening_ge`, `buying`, `selling`, `aborting`, and `collecting` all block.

All other state (held items, GE interface, location) either persists across hops/logouts or is transient. `shouldPauseForHopBoundary(bot)` pauses `tickLogic()` to prevent starting new actions while a forced hop is waiting to dispatch. When a hop is due but a flow is active, the hop stays `forceHopPending = true` with `nextHopAtMs` unchanged, so it retries every tick until the gate passes — no far-future rescheduling is introduced.

## Break system

The mercher takes three types of logout breaks:

- **Top-of-hour pause** (6 min, :59→:05 UK time): The flips script (`determine-flips.mjs`) fetches fresh price data at the top of each hour. Between :59 and :05 of every hour (UK time), the bot pauses all activity and logs out. This only triggers when the auto-loop has signalled it's idle (`loopIdleForBreak = true`) — meaning the current auto-loop iteration has finished and no flow is in progress. The bot never logs out mid-flow. The hour-pause triggers immediately (no random delay) and ends at :05 UK time, at which point the normal break-end logic logs the account back in. If the bot is idle and the hour-pause starts within 2 minutes (`HOUR_PAUSE_SUPPRESS_SHORT_BREAK_MS`), the bot logs out immediately for the hour-pause (target end = :05 UK time) instead of taking a short break — this keeps the bot logged out for the full gap + pause window (~7-8 min) rather than sitting idle for 2 min then logging out for 6 min. GE offers continue filling while logged out. The `breakType` is `'hour_pause'` and the overlay shows "Hour Pause (Xm Ys)". Helpers: `isInHourPauseWindow()`, `getHourPauseEndMs()`, `getNextHourPauseStartMs()` in `antiban/session.ts`.
- **Short breaks** (1-10 min, ETA-based two-tier 50%/90%): Triggered when the auto-loop has nothing to do (all slots occupied, nothing to collect/sell/buy). The auto-loop sets `bot.loopIdleForBreak = true` when it reaches the idle branch. The break system in `breakStep()` checks these flags but enforces a **randomised tick-based delay** before actually logging out:
  - Base: 5-20 ticks
  - + 3 ticks (20% chance)
  - + 1-10 ticks (10% chance)
  - + 5-15 ticks (1% chance)
  
  The delay is computed once when the bot first becomes idle and stored in `bot.shortBreakDelayTicks`. This prevents logging out immediately while adding humanised randomness. The idle tick is reset whenever the auto-loop performs an action (set at the top of `autoLoopTick`).

  **Break duration**: When the auto-loop goes idle, it computes `bot.nextActionEtaMin` — the minimum remaining time (in minutes) until the next action on any slot. For each active slot, this is the earlier of:
  - **Completion**: the offer filling fully (100% of ETA)
  - **Stale abort**: the offer hitting its ETA abort threshold (90% for multi-qty buys with <50% progress; min(125%, ETA-scaled absolute cap for 0-fill buys — `clamp(eta * 0.5, 15, 60)` for non-lowball / `clamp(eta * 0.5, 30, 90)` for lowball via `computeBuyZeroProgressCap`, so fast items keep the 15/30min floor while slow items like Ancient essence at 64min ETA get up to 60/90min; **all buy abort thresholds are scaled by a profit/hr factor** via `computeBuyProfitScaleFactor` — high profit/hr items get up to 2.5x more patience because the opportunity cost of freeing the slot is higher, especially when the item pool is exhausted; thin-margin items ≤3gp are excluded); ETA-scaled no-progress for partial-fill buys — `clamp(eta * 0.25, 10, 30)` min since progress last increased; min(20min absolute, 75-95% of ETA) for 0-progress sells; 75-95% for sells with <25% progress, scaled by profit margin via `computeSellEtaAbortRatio` (minimum 75% raised from 35% — high-value items have high Poisson noise and need more time to clear); 100% otherwise)

  The break system uses `sampleEtaBasedBreakDuration()` to convert this hint into a break duration using a **two-tier strategy** to prevent rapid login/nothing-to-do/logout cycling:
  - **First break** (`checkedAtHalfEta = false`): `nextActionEtaMin * 0.5 * (1 ± 15% jitter)` — logs back in at 50% of the ETA to check for early completions (items that bought/sold quicker than expected).
  - **Second+ break** (`checkedAtHalfEta = true`): `nextActionEtaMin * 0.9 * (1 ± 15% jitter)` — logs back in at 90% of the remaining ETA, aligning with the buy multi-qty abort threshold (90% of ETA + <50% progress). This prevents the rapid cycling that occurs when the bot logs in at 50%, finds nothing ready, takes another 50% break, and repeats with increasingly short breaks.
  - The `checkedAtHalfEta` flag is set to `true` when a short (ETA-based) break starts, recording that the bot has already performed its first 50%-ETA check. It is cleared back to `false` only when a **genuine GE action** completes in `auto-loop.ts` — specifically: a successful buy offer placement, sell offer placement, abort, collect-to-inventory dispatch, or a completed-sell sweep (100% sold). It is **NOT** cleared by login, logout, hop, disconnect recovery, `resetInFlightActionState()`, the unexpected-logout handler, or the `!wasIdle` block at the top of the auto-loop. This persistence is what makes the 50%→90% escalation work across logins: without it, every post-break login resets to a 50% check and the bot cycles rapidly (login → nothing ready → short 50% break → repeat). Transient idle fields (`loopIdleForBreak`, `loopIdleSinceTick`, `shortBreakDelayTicks`, `nextActionEtaMin`) are still cleared on those transitions, but `checkedAtHalfEta` is preserved.
  - Both tiers are clamped to a **3 min minimum floor** (`MIN_LOGOUT_BREAK_MIN = 3`) and **5 min ceiling** (`MAX_LOGOUT_BREAK_MIN = 5`). The 3 min floor ensures every account stays logged out for at least 3 minutes — gives GE offers time to fill before the bot logs back in and potentially aborts them. The 5 min cap ensures the character never stays logged out longer than 5 minutes due to a sampled short or ETA-based break — if something happens sooner than expected while logged out, the bot returns promptly. If no ETA data is available (`nextActionEtaMin <= 0`), falls back to `sampleShortBreakDuration()` (random 3-5 min + profile variance/long-tail, clamped to 3-5 min). Note: this is the **break duration** (how long the account stays logged out before the break-end logic checks for re-login). The **rotation re-login floor** is separate — `MIN_ACCOUNT_BREAK_MS = 10 min` in `account-rotation.ts` clamps the `minBreakDurationMs` recorded per account, preventing an account from being re-selected by `selectNextAccount()` until 10 minutes have elapsed since its logout. The hour-pause break is exempt from this 10-min rotation floor (it passes `enforceMinBreak=false`).

  This ensures the bot logs back in early enough to catch quick fills on the first check, then waits until abort thresholds are about to trigger on subsequent checks — instead of cycling rapidly with ever-shorter breaks.

  **Stay-logged-in override** (`STAY_LOGGED_IN_ETA_THRESHOLD_MIN = 1.0`): When the idle delay expires, if `nextActionEtaMin` is between 0 and 1.0 min (≤ 60 seconds), the bot stays logged in instead of logging out. It resets the idle timer to a short 5–8 tick (~3–5s) re-check interval and returns `false` so the auto-loop continues processing. This prevents rapid login/nothing-to-do/logout cycling when all slots are occupied and an offer is about to complete or hit an abort threshold within the next minute. The stay-logged-in branch does **not** set `checkedAtHalfEta`, so the 50%→90% escalation is preserved for the subsequent real break. The auto-loop recomputes `nextActionEtaMin` on each idle tick, so the bot catches the action as soon as it's due. If the ETA moves back above 60s (e.g. an offer's progress extended the threshold), the bot proceeds with normal logout behavior.
- **Nightly sleep** (4.5-7.5h): Per-account profile with wake-first scheduling. Bedtime = wake time − sleep duration.

All three break types log the player out via `logoutForBreak()`. GE offers continue filling while logged out. After the break duration elapses (wall-clock), `wallClockStep()` → `loginStep()` logs the account back in. The hour-pause check runs after the nightly sleep check and before the short break check in `breakStep()`.

`loopIdleSinceTick`, `shortBreakDelayTicks`, and `nextActionEtaMin` are reset in all the same places as `loopIdleForBreak`: `resetBreakState()`, login recovery, nightly break start, short break start, and at the top of `autoLoopTick()`.

## Multi-character account rotation

The bot supports rotating through a roster of accounts. Each account runs the full auto-merch loop until it goes idle (all slots occupied, nothing to collect/sell/buy), logs out, and the next eligible account logs in. This happens continuously — the bot does not wait for the current account's break to end before switching; it immediately checks the next account in the roster.

### Settings

- **`accountRoster`** (visible string setting) — comma-separated character names (e.g. `"Cyber4Gras,Account2,Account3"`). When 2+ names are listed, rotation is enabled. When empty or a single name, the bot behaves as a single-account bot (no rotation — same account relogin after every break).
- **`profitDisplay`** (visible string setting, read-only) — shows each account's net profit (sum of all completed merch cycles' profits minus losses) as a human-readable string, e.g. `"Cyber4Gras: +1,234,567gp, Ba112: +392,932gp"`. Updated after each completed sale and on logout via `updateProfitDisplay()` in `general/dump.ts` — never per-tick, so there is no performance impact. This ensures the display stays current when idle activity keeps the bot logged in for long periods without a logout. The setting is written by the bot and read by the user; editing it has no effect (the bot overwrites it on the next completed sale or logout). Account order: roster accounts first (in roster order), then any accounts with merch history not in the roster. Accounts are deduplicated by normalized name (all whitespace chars including non-breaking spaces replaced with regular space, collapsed, trimmed, lowercased) so that casing/whitespace differences between the game's `localPlayer.name` and the roster entry don't cause the same account to appear twice with different totals. Pure JSON parse + string formatting — no native SDK calls.
- **`rotationIndexSetting`** (hidden) — stores the current rotation index (which account to check next). Persisted across hot reloads.
- **`accountBreakStateSetting`** (hidden) — stores per-account break state as JSON: `{ accountName: { lastLogoutAtMs, minBreakDurationMs, lastLoginAtMs } }`. Used to determine if an account's minimum break has lapsed and to break ties when multiple accounts are eligible simultaneously.

### Rotation model

1. Account A runs the full auto-merch loop → goes idle → takes an ETA-based short break (or nightly sleep) → logs out.
2. On logout, the account's break state is recorded: `lastLogoutAtMs = now`, `minBreakDurationMs = max(breakDuration, 10 min)` (the ETA-based duration for short breaks, or the full sleep duration for nightly sleeps, clamped to a 10-minute minimum so accounts don't get re-selected too quickly during rotation). The hour-pause break is **exempt** from the 10-min floor — it passes `enforceMinBreak=false` to `recordAccountLogout()` so it keeps its own 6-minute duration (time-bounded by the :05 wall clock). The `lastLoginAtMs` from any existing state is preserved.
3. **Immediate rotation check**: right after the logout completes, `tryImmediateRotation()` calls `selectNextAccount()` to check if a *different* account is eligible right now. If so, the bot skips the break wait and logs in the next account immediately. If no other account is eligible (all sleeping or on break), the bot waits for the break timer.
4. **Periodic idle-rotation check**: while waiting for the current account's break to end, `wallClockStep` periodically (every 10 seconds, throttled via `lastIdleRotationCheckMs`) calls `tryImmediateRotation()` to check if a different account has become eligible in the meantime (e.g. its shorter break elapsed while the current account's longer break is still running). If so, the bot rotates immediately instead of wasting time waiting for the current account's break. This prevents the gap where account B becomes eligible but the bot doesn't notice until account A's break ends. The "no eligible accounts found" log from `selectNextAccount()` is deduplicated to once every 10 seconds (`lastNoEligibleLogMs` in `account-rotation.ts`) to prevent duplicate messages when the break-step logout path and `wallClockStep` poll both call `selectNextAccount()` in the same tick. `tryImmediateRotation()` logs the rotation itself ("Rotation: X logged out — immediately rotating to Y"); the `wallClockStep` caller does not add a redundant second log.
5. When the break timer expires (and no immediate or idle rotation happened), `selectNextAccount()` selects the next account using a **time-based** policy (not roster order):
   - Skip any account currently in its nightly sleep window (checked via its SessionProfile).
   - For each remaining account, compute `breakEndMs = lastLogoutAtMs + minBreakDurationMs` (0 if no break state → eligible now).
   - Skip accounts whose `breakEndMs > now` (minimum break hasn't lapsed).
   - Among eligible accounts, pick the one with the oldest `lastLoginAtMs` (longest since last login). Accounts that have never logged in (`lastLoginAtMs = 0`) get highest priority. This prevents starvation — if multiple accounts' breaks end within the same 10-second poll interval, the one that hasn't been logged in for the longest gets priority rather than the one that happens to be first in the roster.
   - The "soonest break end" timing is handled by the 10-second periodic poll and `getSoonestBreakEndMs()` — the bot checks for eligibility at the right time, and when multiple accounts are eligible, the `lastLoginAtMs` tiebreaker decides.
6. The selected account's credentials are staged and the bot logs in. On successful login, the account's break state is updated: `lastLogoutAtMs = 0`, `minBreakDurationMs = 0`, `lastLoginAtMs = now` (preserving the entry for the tiebreaker rather than clearing it).
7. The new account runs the full auto-merch loop, and the cycle repeats.

### Rotation over idle activity

When the current account is performing an idle activity (chocolate dust, ultra compost, or goat horn dust) and a **different** account becomes eligible (its break lapsed or it woke up), the current account cleans up and logs out so the eligible account can log in. Without this, the current account keeps grinding the idle activity until its own nightly break, leaving the eligible account waiting.

- The auto-loop's idle-activity dispatch (`auto-loop.ts`) calls `isRotationDueForLoggedIn(bot)` every 10 seconds (throttled via `bot.lastLoggedInRotationCheckMs`). This helper delegates to `selectNextAccount()` and returns the eligible account's name only if it's **different** from the current account.
- When rotation is due, the `geActionDue` flag passed to the idle-activity tick handler (`chocolateDustTick`/`ultraCompostTick`/`goatHornTick`) is set to `true`. The idle activity transitions to its cleanup phase (banks all idle items, closes the bank) and returns `false`, yielding to normal GE logic.
- The auto-loop falls through to the idle branch, sets `loopIdleForBreak = true`, and the break system logs out with the normal randomised pre-logout delay (5-20 ticks + variance). `tryImmediateRotation()` then picks the eligible account.
- The 10-minute minimum re-login floor (see step 2 above) prevents the just-logged-out account from being immediately re-selected, avoiding rapid cycling.
- Single-account mode (roster < 2) is unaffected — `isRotationDueForLoggedIn` returns `null`.
- The nightly break still fires regardless of idle activity (it doesn't check `loopIdleForBreak`).

### Chat-triggered GE yield during idle activity

When a GE offer completes while an idle activity is active, the `onChatMessage` handler detects the "Grand Exchange: Finished buying/selling X" game message and sets `bot.geOfferCompletedChatMs`. The idle-activity dispatch checks this flag each tick and, if set, forces `geActionDue = true` — triggering the same cleanup phase (bank all idle items, close bank, yield to GE operations) as the ETA-based timer. This lets the bot collect, sell, and place new offers immediately when an offer completes, instead of waiting for the `idleActivityGeActionDueMs` timer to expire. The flag is only set when `idleActivityPhase !== 'none'` so normal GE operations (where completions are handled by the collect/sweep flows) are unaffected. Reset in `resetAutoLoop` and `resetInFlightActionState`.

### Overlay (minimal mode-label + start time)

The overlay was stripped to the absolute minimum to eliminate per-frame allocations and native handle accumulation from the render path. It draws one rect + two text lines: the current autoMode label (Paused / Normal / Slow / F2P) from `bot.overlayStatusText`, and a "Start: HH:MM" line from `bot.sessionStartUKTime` — both plain-JS fields updated only in `onEnable` / `onDisable` / `onSettingChanged`. The render callback does zero allocations, zero `Date.now()`, zero native SDK reads, zero cache lookups. The start time is captured once per client session via a module-level cache (`sessionStartUKTimeCache`) that survives plugin toggles but resets on a full client reload. All previous overlay content (Status, TIMERS, Session timer, Next Account, Next Hop, Sleep/Wake Time, formatUKTime memoization, 2-second overlay cache, Daily Profit, Fatigue, Delay) has been removed.

### Per-account data (already isolated by account name)

- Offer cache, merch history, abort history, daily profit, session profile, hop state — all per-account, unchanged.
- Buy-freeze state — global (not account-keyed), unchanged.

### Cross-account item overlap

Multiple accounts are allowed to merch the same item concurrently. The buy scan does NOT deduplicate items across accounts — each account independently selects items from `merchableItems.json` based on its own cash stack, occupied slots, buy limits, freezes, and membership. This intentionally accepts buy-side price competition and capital concentration in exchange for letting each account pick the highest-ranked item it can afford. (A previous cross-account deduplication layer was removed at the user's request.)

### Sleep/wake schedules

Each account's sleep/wake schedule comes from its own `SessionProfile` (deterministic per account name). The `isAccountSleeping()` function in `account-rotation.ts` checks if the current wall-clock time falls within the account's sleep window (computed from `nightlySleepLengthBase` and `nightlyWakeBase`). If an account is sleeping, it is skipped during rotation. If all accounts are sleeping, the bot waits (retrying every 30 seconds). If only one account is awake, the bot cycles that one account respecting its break state — effectively behaving as a single-account bot until other accounts wake up.

### Nightly sleep with rotation

When an account's nightly sleep triggers, it logs out and its break state is recorded with the full sleep duration. The rotation then checks the next accounts — if they're also sleeping, the bot waits. When an account wakes up (its sleep window ends), it becomes eligible and the bot logs it in. The rotation index continues from where it left off — there is no "reset to first account" each morning.

### Single-account fallback

When `accountRoster` is empty or has a single name, `isRotationEnabled()` returns false and `selectNextAccountForLogin()` returns the current account name. The bot logs back into the same account after every break — identical to the pre-rotation behavior.

### Startup account selection (fresh tab / client restart)

When the bot starts while logged out (e.g. after a client tab restart), `bot.currentPlayerName` is empty and `wallClockStep` must determine which account to log in. The native Titan client persists its own last-used account across restarts (separate from the plugin's hidden settings, which do NOT survive client restarts), so `titan.state.login.snapshot().displayName` may return a stale account that is not in the roster (e.g. "Avaer98" when the roster is "Cyber4Gras,Ba112").

The account-selection block in `wallClockStep` resolves this with a roster-validated priority order:

1. **Snapshot displayName** — used only if it is in the roster (when rotation is enabled) or unconditionally (when rotation is disabled).
2. **`lastActiveAccountSetting`** — used only if it is in the roster (when rotation is enabled) or unconditionally (when rotation is disabled). This setting is empty on a fresh client restart, so it only helps during hot reloads.
3. **`selectNextAccount()`** — when rotation is enabled and neither of the above is in the roster, the bot selects the next eligible account from the roster using the normal time-based selection policy.

When rotation is disabled, the behavior is unchanged — the snapshot displayName or lastActiveAccount is used without roster validation.

## Login retry timeout

`tryStageAndSubmitLogin()` tracks `bot.loginFirstAttemptAtMs`. If 5 minutes elapse without login, the bot terminates. A 10-attempt `submitCredentials` limit is a faster failure path. `loginIndex === 10` (or legacy `2`) means staged; `loginIndex === 9` covers both "game update in progress" and "you were signed out" — the snapshot doesn't expose message text, so we can't distinguish them. Index 9 uses exponential backoff (5s → 10s → 20s → 40s → 60s cap) with credential re-staging on each retry. If it's "signed out", the first fast retry succeeds. If it's a game update (which can last 30+ min), we back off to avoid hammering the login server. When a staged profile is first detected, the bot **re-stages** with `bot.currentPlayerName` before submitting — this ensures the staged profile matches the intended account after multi-account rotation (the OSRS client may still have the previous account's profile staged).

## Post-login settle delay

After the title screen disappears and the player is in-world, `loginStep()` sets `bot.postLoginResumeAtMs = now + createDelay(8, 12, 18) ticks` (4.8-10.8s humanized settle). `tickLogic()` blocks until this elapses, giving the client time to render the world and load 3D models (graph nodes). After clicking "Click here to play", `postLoginResumeAtMs` is set to `MAX_SAFE_INTEGER` to block until the title disappears; the title-gone re-check interval is 8 ticks (~4.8s). When the settle completes, failure counters are reset (the login transition can cause false strikes e.g. GE not openable while the world is still loading). The settle delay was increased from 3-5 ticks (1.8-3s) to 8-12 ticks (4.8-7.2s) base with an 18-tick (10.8s) cap because the shorter delay caused the first GE-open click after login to land on a leftover `text=Play` widget — the clerk/booth graph nodes were still NULL, so ClickSafety sanitized the click to wrong coordinates and the GE didn't open, wasting ~3s on a retry.

**Critical: `breakStep` must NOT call `resetLoginState` when `postLoginResumeAtMs > 0` or while the title screen is still being handled.** When `breakPhase === 'logging_in'`, `breakStep` calls `loginStep()` which may detect the title screen (setting `titleFirstSeenAtMs`) or click it (setting `postLoginResumeAtMs = MAX_SAFE_INTEGER` while waiting for it to disappear) or set a settle delay. If `breakStep` then calls `resetLoginState()`, it wipes both `titleFirstSeenAtMs` and `postLoginResumeAtMs` to -1, and neither the title-screen guard at the bottom of `breakStep` nor the settle delay in `tickLogic()` ever runs — the auto-loop walks to the GE while the "click here to play" screen is still visible and the GE-open click resolves to `text=Play`. This race is most common after a reload during login, when `isWorldReady()` returns true on the same tick the title screen appears (so the in-world branch fires before the login FSM has had a tick to click the title). The fix has three parts: (1) after `loginStep()` in the logged-out `logging_in` branch, if `titleFirstSeenAtMs > 0 || titleWaitingForGone`, return early without clearing the break state — let the login FSM click the title on a subsequent tick; (2) the logged-in `logging_in` branch (which runs when `isLoggedIn` is true but `breakPhase` is still `logging_in`) also calls `loginStep()` before checking `isInWorld()` and has the same title guard — without this, `isLoggedIn` transitioning to true while the title screen is visible would skip the logged-out branch (which calls `loginStep`), leaving `titleFirstSeenAtMs` at 0, so the title guard at the top of the "Player is logged in" section never fires; (3) once the title is gone and `isInWorld()` is true, preserve `postLoginResumeAtMs` and `loginSettled` across `resetLoginState` calls so the settle delay isn't wiped. The post-login settle logic in `tickLogic()` handles the cleanup when the settle delay elapses.

## Reset Break ends an active break immediately (for future implementation)

When breaks are implemented, `resetBreak()` should call `resumeFromBreak()` when `breakPhase === 'BREAK_ACTIVE'`, instead of only clearing session targets.

## Bank interactions (for future implementation)

When banking is implemented, the following rules apply (adapted from mixology):

- **Bank chest is a toggle — no doubleClick**: The GE clerk / bank chest is a toggle — clicking it when open closes it. `openBank()` must NOT use `doubleClick: true`. The `doubleClick` option is only safe for idempotent targets.
- **Bank open click in-flight guard**: `bot.bankOpenClickInFlight` is set to `true` inside `openBank()` before the click dispatch. While true, `openBank()` returns early. Cleared when bank opens, on timeout, on rejection, and in `resetInFlightActionState()`.
- **Inventory-open guard after hop/login**: `tickLogic()` has a post-hop/post-login block (after the `hopResumeAtMs` delay and post-login settle, before `shouldPauseForHopBoundary`) that ensures the inventory tab is open before the auto-loop runs. The world switcher can stay open after `hopIngame()` completes; interacting with widgets while it is visible can trigger native null exceptions that auto-disable the plugin. The block: (1) if GE or bank is open, skips — both have their own inventory views and Escape would close them; (2) if the world switcher is open, sends Escape and returns (waits a tick); (3) sends Escape once to close lingering full-screen interfaces; (4) clicks the inventory tab widget (packed 10551358) via `ensureInventoryOpen()` in `general/helpers.ts`. The `inventoryOpenEnsured` flag gates the Escape-once and ensures the sequence runs only once per hop/login. It is reset to `false` in `completeHop()`, on post-login settle completion, and in `resetHopState()`.
- **Bank open delay**: When `bankRun()` first observes `bank.isOpen`, wait 1 tick 95% of the time, or 2-3 ticks the remaining 5%, before starting any withdrawal. This stops the bot from withdrawing on the same tick the bank interface appears.
- **Bank close via Escape**: Use `titan.keyboard.sendKey(titan.keyboard.Key.Escape)` instead of `titan.utils.bank.close()`. The `bank.close()` API can throw "widget arg11 builder was unavailable"; Escape is a safer, synchronous close that takes the same WndProc path as a hardware key press.
- **Diurnal pace (fatigue) applies uniformly**: The diurnal pace multiplier is applied inside `createDelay()` itself, so all action delays scale with fatigue. The mercher does not perform banking actions — if banking were added in the future, those calls should bypass the pace multiplier (pass a flag or use a raw delay) since a tired player still clicks deposit/withdraw quickly.
- **Banking actions excluded from jitter amplification**: A spontaneous 3-18s pause mid-banking is unnatural. Humans pause before opening or after closing the bank, not mid-banking. If jitter amplification is implemented, banking actions must be excluded.
- **Withdraw-X dialog handling**: `titan.utils.bank.withdrawItemAmount(itemId, amount)` opens the OSRS "Withdraw-X" dialog but does not type the amount or press Enter. However, it can also withdraw directly without opening a dialog (when the bank's last-used X amount matches). Handle both paths: (1) call `withdrawItemAmount`, (2) check if the dialog is open, (3) type the amount via `titan.keyboard.typeString()` and press Enter in the completion callback, OR proceed immediately if a direct withdrawal happened.
- **Withdraw-X dialog detection**: `titan.utils.bank.isSearchOpen` may not reliably return `true` for the amount entry dialog. Fall back to `titan.state.widgets.findByText('Enter an amount')` (direct native lookup, sub-millisecond) instead of expensive recursive widget queries.
- **Withdraw-X set once per script run**: The bank remembers the last X amount. After typing an amount once, `withdrawItemAmount(id, amount)` withdraws directly without opening a dialog. Track this with a flag so subsequent withdrawals skip the dialog detection phase.
- **Bank-open guard on `withdrawing`**: The `withdrawing` case must check `titan.utils.bank.isOpen` before querying bank contents. After a break or hop, the bot resumes in its pre-break state but the bank is closed — `bank.contains()` returns false when the bank isn't open, causing false "out of supplies" termination.

## Current bot behaviour

- The plugin has four modes via the `autoMode` combo setting:
  - **Paused** (default, value 0): No script logic runs at all — no login, no breaks, no hops, no merching. All loop callbacks (`onGameTick`, `onMainLoop`, `onGameStateChanged`, `onChatMessage`) return immediately. The overlay still renders so the user can see the status and switch to Normal or Slow. This is the safe default for new clients — the bot does nothing until the user explicitly switches to Normal or Slow.
  - **Normal** (value 1): The bot runs the full automated merching loop: login, breaks, hops, GE-open check → collect → stale → sell → buy. The buy scan uses the default non-lowball-first tier order.
  - **Slow** (value 2): Same loop as Normal, but the buy scan prepends a preferred tier that targets lowball items with a runtime buy ETA of 30–60 minutes (relaxed 240min turnover cap) ahead of the normal tier order. These slower, higher-margin fills suit the ~30-minute account login cadence. If no item qualifies, the scan falls through to the normal tier order unchanged — fast non-lowball flips remain eligible. Slow Mode does NOT alter login/logout/break/rotation/hop timing; it only changes buy-offer item selection. Pre-sleep lowball priority takes precedence over Slow Mode when active (pre-sleep is the stronger condition and already does lowball-first with the 240min cap).
  - **F2P** (value 3): Same loop as Normal, but reads `f2pMerchableItems.json` (curated high-volume F2P items, fixed 1gp margins, relaxed runtime thresholds). Slot count still uses `isMembersWorld()` — 3 slots on F2P worlds, 8 on P2P.
- The mode persists across hot reloads (it's a Titan setting). Switching from Paused to Normal or Slow re-runs the startup audit on the next tick so the auto-loop reconciles from current GE state. Switching from Normal/Slow to Paused stops all logic immediately on the next tick.
- The `Start/Stop Script` button (`startStop` buttonSetting, position -2 — top of the settings panel) toggles the mode programmatically — identical to switching the Mode combo. Stop saves the current mode to `lastActiveMode` (persisted via the hidden `lastActiveMode` setting — hot-reload only) and writes `autoMode.value = 0`; Start writes `autoMode.value` back to the last active mode. A `terminated` bot counts as stopped — clicking the button runs `resetForResume()` (same recovery as a plugin toggle off/on, including re-stamping `scriptStartMs` since `terminate()` cleared the setting) before resuming. The button invokes `onSettingChanged('autoMode')` after the write; the mode-change block there is guarded by a previous-value check so it stays idempotent whether or not the native layer fires the callback on programmatic writes.
- The `BuyOfferFlow` is a 21-step state machine. Each action step calls `createDelay(1, 100)` (base 1 tick, 100% trigger chance) and stores the result in `lastDelay`. The caller uses `flow.lastDelay` in `setAction()`.
- When the flow reaches `done` or `failed`, the bot logs the result, clears the flow, and returns to idle.
- `onGameTick` always runs `gameTick`; it does not require `isRunning` to be true.
- Logging is split into three tiers:
  - **Errors** (always logged): parse/save failures, offer placement failures, `onMainLoop` errors, termination reasons, manual button-triggered dumps. These are unconditional `titan.logf` calls.
  - **Info** (controlled by `logInfo` boolean UI setting, default `true`): important, uncommon events — account rotation, break start/end, login/logout, world hops, offer placement/abort success, cache reconciliation, item freezing, repricing, startup audit, mode switched, tick counter reset, unexpected logout, post-login settle. Gated by `bot.logInfo.value` via the `humanLog` helper (in `session.ts`, `hopper.ts`, `login.ts`) and `infoLog` helper (in `auto-loop.ts`), or inline `if (bot.logInfo.value)` / `if (this.logInfo.value)` checks.
  - **Debug** (controlled by `logDebug` boolean UI setting, default `false`): verbose per-tick diagnostics — slot summaries, GE open clicks, idle activity diagnostics, click logging, delay/humanisation layers, cache cleanup details. Gated by `bot.logDebug.value` via the `debugLog` helper or inline checks.
  - With `logInfo` off and `logDebug` off, only errors and manual dumps are logged.
- The offer cache is persisted in a hidden string setting (`offerCache`) and survives hot-reloads. It is scoped per in-game player name. Includes duplicate account-key migration on load.

## OSRS Grand Exchange buy offer flow (in-game mechanics)

1. Click "Create buy offer" button on any empty slot (1-8 for members, 1-3 for F2P) in the GE main UI.
2. The "What would you like to buy?" UI shows in the chatbox area — this is when we type the item name.
3. As you type, all items containing the typed text appear in a scrollbox in the chatbox UI area — results update live with each character.
4. The item is clicked from the results list — `scanSearchResults(itemName)` finds the exact case-insensitive match and `clickSearchResult(matchIndex)` clicks it by child slot. Pressing Enter is NOT used (it selects the first result, which can be wrong — e.g. "Charcoal" when searching "Coal"). **Early-stop**: while typing is in progress, `scanSearchResultsUnique(itemName)` is checked each tick — if the desired item is the only visible result, typing is cancelled early (e.g. "magp" for "Magpie impling jar"). A 40% chance of a 1-2 tick "looking" delay applies before clicking.
5. The selected item is loaded into the "Set up offer" window — this is where quantity and price are configured. Defaults: quantity 1, price = market price.
6. The "..." button on quantity or price is clicked, which displays "How many do you wish to buy?" or "Set a price for each item" UI dialogue in the chatbox area respectively.
7. After typing a quantity/price and pressing Enter, the "Set up offer" UI updates with the specified values.
8. The "Confirm" button is pressed to place the offer.
9. The "Set up offer" UI closes and we're back at the main GE UI.

**Important**: Search results appear *while typing* (before Enter), not after Enter. The buy-offer flow scans `GE_SEARCH_RESULT_TEXT_WIDGET` (10616884) children for an exact name match and clicks that specific result via `clickWidget(10616884, matchIndex, 1)` — same CC_OP(57, 1, childSlot) pattern used for offer slots and confirm. If no exact match is found, the flow fails with a clear error.

## Auto-merch architecture

### Mode toggle

The `autoMode` combo setting selects between `Paused` (0, default), `Normal` (1), `Slow` (2), and `F2P` (3). In Paused mode, all loop callbacks (`onGameTick`, `onMainLoop`, `onGameStateChanged`, `onChatMessage`) return immediately — no script logic runs at all. The overlay still renders so the user can switch modes. In Normal, Slow, and F2P mode, the bot runs the full automated merching loop (login, breaks, hops, GE actions); Slow differs only in buy-scan tier order (it prepends a lowball 30–60min buy-ETA preferred tier) and F2P reads `f2pMerchableItems.json` with relaxed thresholds. Switching from Paused to an active mode re-runs the startup audit; switching to Paused stops all logic on the next tick. The `Start/Stop Script` button writes `autoMode.value` directly to toggle between Paused and the last active mode (`lastActiveMode`, persisted via the hidden `lastActiveMode` setting); on a `terminated` bot it runs `resetForResume()` first. `isRunning` mirrors `autoModeValue !== 0` for parity with the other plugins — it is informational only, not a gate.

### Startup audit

On the first tick in Normal or Slow mode (either on script start or when the user switches from Paused to Normal or Slow), the bot audits the current GE state (is GE open? is offer config screen showing? which slots are occupied?) and logs active slots for visibility. If a GE sub-screen (offer config / search / quantity / price prompt) is open, a one-time Escape is sent to close it — the auto-loop then reopens the GE and starts fresh flows. No flow reconstruction is attempted. This is safe because interrupted buys lost nothing (no items spent), interrupted sells still have items in inventory (re-listed by the sell scan), and already-placed offers in GE slots are unaffected. The audit is skipped entirely in Paused mode (the `onGameTick` callback returns before the audit runs).

**Title-screen deferral**: The audit is deferred if the player is on the title screen or settling after login. The check uses `isTitleScreenVisible()` (exported from `antiban/login.ts`, single targeted widget lookup) OR `titleWaitingForGone` OR `postLoginResumeAtMs > 0`. If any is true, the audit waits for the next tick (logged once to avoid spam). This prevents the audit from logging a misleading `screen=closed, geOpen=false` state while the title screen is visible. The existing login FSM remains responsible for clicking the title screen. The audit runs on the first tick after the player is in-world and all title/login/settle state has cleared.

### Offer cache persistence

The offer cache is stored in a hidden string setting `offerCacheSetting` (key `offerCache`, default `'{}'`, `hidden: true`). The cache is a JSON object keyed by in-game player name, each containing a per-account `OfferCacheData` map from item name to `OfferCacheEntry`. This mirrors the mixology bot's `humanizationState` persistence pattern. `loadOfferCache` includes a normalized key fallback for defensive casing/whitespace tolerance.

- **Load**: `OfferCacheManager` constructor calls `loadOfferCache(bot, accountName)` on first access (lazy). `ensureCache()` detects account rotation (when `bot.currentPlayerName` differs from the cache manager's bound account name) and reloads the cache with the new account — saving the old account's cache first so pending sells are persisted. Without this, the cache manager would remain bound to the old account while profit attribution uses the new account, causing cross-account profit attribution.
- **Save**: After every mutation (offer placed, price revised, entry removed), `cache.save()` writes back to the hidden setting. Uses the existing canonical key if one matches under normalization, to avoid re-creating duplicate keys with different invisible whitespace.
- **Hot-reload only**: The hidden setting survives plugin hot-reloads (off/on within the same client session) but does NOT reliably persist across client restarts. After a client restart, the cache may be empty while GE offers remain on the server. Reverse reconciliation (below) reconstructs missing entries from live GE slots.
- **Duplicate account-key migration**: On load, keys that differ only by invisible whitespace characters (e.g. non-breaking space U+00A0 vs regular space U+0020 — both look like "hc fruitz" but are different JSON keys) are merged under a canonical key (roster match preferred, else first-seen raw key). For items present in multiple duplicate keys, the entry with the highest `offerPlacedAt` (most recent) wins. Write paths also use the existing canonical key to prevent re-creating duplicates.
- **One entry per item**: A slot can only contain a single item, so one cache entry per item name is sufficient.

### Reverse reconciliation (cache loss recovery)

When the cache is lost after a client restart, active GE offers survive on the server but have no cache entry. Without reconstruction, staleness checks bail out (they need `offerPlacedAt`), completed sells lose their profit, and stuck offers sit forever. Reverse reconciliation runs once on the first GE-open tick after script start (Step 2c, immediately after orphan reconciliation):

- Iterates over occupied slots with a known item name and type (`buy` or `sell`). **Truncated names** (ending with "...") are resolved to the full name via the slot's itemId in `getOfferSlotState()` before this step runs — see the `grand_exchange/widgets.ts` entry above.
- For each slot with no existing cache entry, calls `cache.reconstructEntry()`.
- **Offer price from GE slot**: The per-unit offer price is parsed from the GE slot's `priceText` widget (e.g. `"2,069 coins"` → `2069`). For sell offers, this becomes `sellPrice`; for buy offers, `buyPrice`. This is the actual price the bot typed when placing the offer — using it instead of the 1h market average prevents false loss/profit recording (e.g. Twinflame staff sold at 8.7M but 1h average was 8.6M, producing a false -105k loss after tax). If `priceText` is null or unparseable, falls back to merch/priceHistory prices.
- **Buy price** (for sell offers) and **sell price** (for buy offers) come from `merchableItems.json` (primary) or `priceHistory.json` (1h average fallback for items no longer in the merchable list). If the priceHistory data is stale (>10 min old, meaning `determine-flips.mjs` has stopped), reconstruction still proceeds (so the offer is managed) but a warning is logged — the offer is already live on the GE and leaving it unmanaged is worse than reconstructing with approximate prices.
- **ETAs** are recalculated from the actual offer quantity using `computeRuntimeEtas()` (the same runtime ETA formula: 50% market share, 15% 2h buffer, lowball penalty, `BASE_FILL_TIME_MIN`), **capped at 120 minutes** via `RECONSTRUCTED_ETA_CAP_MIN`. For merch items, this produces accurate ETAs based on the actual offer quantity rather than the 50m simulation quantity (e.g. Ancient essence at 124k units gets ~42min buy ETA instead of the 113min simulation ETA). For priceHistory-only items (no longer in the merchable list), ETAs are computed from 1h volume data using the same 50% market share assumption, also capped at 120min. Without quantity-aware recalculation, reconstructed offers would inherit simulation ETAs based on the 50m cash stack allocation, causing the stale checker to wait far longer than it should before aborting genuinely stuck offers.
- `offerPlacedAt` is set to `Date.now()` — the actual placement time is unknown, so the offer gets a fresh full ETA window before staleness checks can abort it. This is the safest choice since aborting an offer we know nothing about could discard partial fills.
- For sell offers, `sellQuantity` is set from the slot's item quantity so the completed-sell sweep can record profit when the sell finishes. `sellConfirmed` is set to `true` (the offer is already live on the GE).
- If no price data is found in either source, the slot is skipped (logged) — the offer is left alone until it completes or the user intervenes.
- **Reconstructed flag**: Reconstructed entries are marked with `reconstructed: true` and `reconstructedBuyPrice: true` on the cache entry. The stale checker uses `reconstructed` to immediately abort zero-profit or very low profit/hr reconstructed sells (see below) — these are pre-existing offers from a previous session whose prices may be stale or no longer profitable, and the slot is better used for a fresh merchable item. The `reconstructedBuyPrice` flag is NOT cleared on re-list (it survives sell abort + re-list cycles) so the completed-sell sweep can skip recording phantom losses from uncertain buy prices; it is only cleared when the bot places a new buy offer (`recordBuyOffer`) with a known price.
- **Mode mismatch fix**: When an existing cache entry's mode doesn't match the live GE slot type (e.g. cache says `buy` but the GE slot is a `sell`), `cache.fixModeMismatch()` corrects the entry. This happens when a plugin reload (e.g. `npm run build`) causes the setting to revert to a stale value — the in-memory sell-mode update is lost, but the GE still has the live sell offer. Without correction, the stale checker uses wrong-mode data (wrong sell price from merchable data instead of the actual sell price, wrong sell ETA, wrong elapsed time from the original buy placement) and may prematurely abort the offer. The fix uses the GE slot's `priceText` as the actual price, resets `offerPlacedAt` to now, applies the value-aware sell ETA cap (same as `recordSellOffer`), and preserves `buyPrice` and buy-limit tracking. Logs: `Cache: fixed mode mismatch for X (buy -> sell, ...)` and `Auto: reverse reconciliation fixed N mode mismatch(es) ...`.

### Reconstructed-sell profit guard

The stale checker (`isSellOfferStale`) applies two abort checks to reconstructed sell entries (bypassing all ETA-based checks):

1. **Zero/negative net profit**: If `netSellPrice(sellPrice) - buyPrice <= -tolerance` (after 2% GE tax), the sell will never make money. The tolerance is `max(5gp, 2% of sell price)` — the reconstructed buy price comes from priceHistory's 1h average (the actual cache was lost), which can differ from the real buy price by 2-3%. For thin-margin items, this small error can flip a profitable sell into an apparent loss (e.g. Toadflax: reconstructed buy=2207 vs actual buy=2160, sell=2224 → apparent -27gp/item loss, but actual +20gp/item profit). Losses within the tolerance are likely reconstruction artefacts and are NOT aborted — the sell stays in the slot and completes normally. Genuine large losses still abort immediately (no grace period) to free the slot. Example: Dragonstone bolt tips at 411gp sell, 403gp buy, 8gp tax = 0gp net profit (within tolerance, not aborted); a 100gp/item loss on a 1000gp sell would exceed the 20gp tolerance and be aborted.
2. **Very low profit per slot per hour**: If a sell ETA is available and `profitPerItem * quantity / (sellEta / 60) < 5000` (5k gp/hr), the slot is worth more than this. Only fires after a **5-minute grace period** (`RECONSTRUCTED_SELL_GRACE_PERIOD_MIN`) AND only if the offer has **0% progress** — thin-margin sells that are actively filling are left alone to complete at the original price rather than being driven to a loss through revision cycles. Example: Raw sea turtle at 6gp/item * 806 qty / 5.1h ETA = ~946 gp/hr.

The 5k gp/hr threshold is lower than the 20k buy-scan threshold because we already own the item — the goal is just to avoid wasting a slot on near-zero profit. Only reconstructed entries are affected; entries we placed ourselves are deliberate picks and follow the normal ETA-based stale rules. The `reconstructed` flag is cleared when the bot places its own sell offer (`recordSellOffer`) and when the offer is confirmed (`confirmSellOffer`), so the guard only fires on the original pre-existing offer, not on the bot's re-lists. The `reconstructedBuyPrice` flag survives re-list cycles and is used by the completed-sell sweep (`isReconLoss`) to skip recording phantom losses when the buy price is uncertain — it is only cleared when the bot places a new buy offer (`recordBuyOffer`) with a known price.

**Reconstructed-loss recording skip**: When a reconstructed sell completes, losses are NOT recorded in merch history or daily profit. The buy price is uncertain (from priceHistory 1h average, not the actual cache), so any loss is unreliable — recording it would create phantom losses (e.g. Toadflax: -16,956gp phantom loss) and trigger phantom loss-history cooldowns (2h buy freeze on a profitable item). Profits are still recorded (conservative — better to under-report losses than over-report them). The skip only applies when `entry.reconstructed && merchProfit < 0` at the time of cycle completion. If the sell was re-listed by the bot (clearing the `reconstructed` flag), the re-list entry's profit/loss is recorded normally — but the tolerance threshold above prevents false aborts, so the original reconstructed sell completes without re-listing in most cases.

### `merchableItems.json` loading

The JSON is imported at the top of `data/merchable-items.ts` and inlined by esbuild at build time. The Titan SDK has no runtime file-system API, so the data is only refreshed when the plugin is rebuilt (which Titan hot-reloads). The external `determine-flips.mjs` process updates the file every 3 minutes; a rebuild + hot-reload picks up the new data.

### Data validity safeguards

`isMerchableDataValid()` in `data/merchable-items.ts` checks two safeguards:

1. **Count safeguard**: `merchableItems.json` must have ≥ 5 items. This only guards against catastrophic pipeline failures (broken Wiki API response or crashed `determine-flips.mjs` run producing 0-4 items). The freshness check is the primary staleness guard.
2. **Freshness safeguard**: The newest `dataFetchedAt` across all items must be within the last 10 minutes. Since `determine-flips.mjs` runs every 3 min, data older than 10 min means the script stopped running or the Wiki API is down.

Both checks run dynamically (not cached) so hot reloads pick up new JSON automatically. The safeguard **only blocks placing new buy offers** — it does NOT block login or offer management. When data is stale:
- The bot still logs in, collects completed sells, aborts stale offers, and sells inventory items.
- The buy scan in `auto-loop.ts` checks `isMerchableDataValid()` before placing new buys and skips with a log message if stale. The skip sets `emptyBuySlot = -1` and falls through to the idle path (short break / logout / rotation) — it does NOT return false, which would skip idle scheduling and cause a tight loop every tick with no delay, no break eligibility, and per-tick log spam.
- The frozen-item swap path (all slots occupied) also checks and skips swaps when data is stale, falling through to the same idle path.
- The overlay status shows `[DATA STALE]` instead of the normal countdown.
- Login, rotation, and break timing are never blocked by stale data — the bot always logs in to manage existing offers. New buys resume automatically when a rebuild brings valid data via hot reload.

### Auto-merch loop order

`autoLoopTick(bot, tick)` runs one tick of the loop:

1. **GE-open check (first)**: If GE is not open, walk to GE if not nearby, then open via `openGe()` (which tries the nearest of clerk NPC or "Exchange" booth object). This is the very first automated operation. A **wall-clock cooldown** (`GE_OPEN_WALL_CLOCK_COOLDOWN_MS = 3000ms`) enforced via `lastGeOpenDispatchMs` on `AutoLoopState` prevents a second GE-open click from being dispatched within 3 seconds of the previous one. This is necessary because the SDK can fire a burst of ticks immediately after login (the tick counter advances several ticks in milliseconds), causing the tick-based action delay to elapse instantly and the loop to re-enter and dispatch a duplicate click before the first one has taken effect. The cooldown is reset to 0 in `resetAutoLoop()` and in the tick-counter-reset block in `stark-mercher.ts` so the first GE-open after a restart/login goes through immediately.
2. **Close GE sub-screens**: If the offer config screen, search prompt, or price prompt is open (e.g. after a script reload mid-flow or a misclick), close it with Escape via `sendKeyWithJitter`. This prevents slot clicks from landing on the sub-screen instead of the intended slot.
3. **Defer to active flows**: If a buy/sell/abort flow is in progress, tick it and return.
4. **Get all slot states**: `auditGeState()` reads all 8 slots via cached widget children.
5. **Cache reconciliation (2b)**: One-time orphan removal — removes cache entries for items not in any GE slot, not in inventory, no active buy-limit window, and no pending sell profit.
6. **Reverse reconciliation (2c)**: One-time cache reconstruction — for occupied slots with no cache entry (lost after client restart), reconstructs entries from `merchableItems.json` / `priceHistory.json` so staleness checks and profit tracking work. Also refreshes unconfirmed sell entries that are clearly live on the GE (in a slot but `sellConfirmed = false`) — resets `offerPlacedAt` to now and marks `sellConfirmed = true` so stale checks measure from the restart time, not the original `recordSellOffer` time (which was before the sell flow started).
7. **Completed-sell sweep + Collect**: The sweep first iterates cache entries with `mode='sell'` and `sellQuantity > 0`. For each entry, if the matching GE slot is `completed_or_aborted` (100% progress, type=sell) and the bot did NOT initiate an abort (no `activeAbortFlow`, no `abortSlotInfo`), and the entry is not reconstructed and is sell-confirmed, the profit is recorded IMMEDIATELY — before the collect click. This prevents profit loss when a hot-reload occurs between the collect and the next tick's sweep (the cache setting may revert to a stale pre-sell state, or `fixModeMismatch` may clear sell fields when a new buy for the same item is already live on the GE). Reconstructed entries are excluded from this pre-collect path. If no slot is `completed_or_aborted`, the sweep also checks for entries where the item is not in any slot or inventory (post-collect path — sell was already collected on a previous tick). After the sweep, if any slot has `status === 'completed_or_aborted'`, click collect and return. A **wall-clock cooldown** (`COLLECT_WALL_CLOCK_COOLDOWN_MS = 3000ms`) enforced via `lastCollectDispatchMs` on `AutoLoopState` prevents a second collect click within 3 seconds of the previous one — same rationale as the GE-open cooldown (tick bursts after login can cause the tick-based delay to elapse instantly). The cooldown is reset in `resetAutoLoop()` and the tick-counter-reset block. Completed sell offers are NOT removed from the cache — entries are kept for buy-limit tracking (see below).
8. **Stale offers**: For each active slot, check stale conditions (sell: ETA-scaled absolute cap for 0-progress sells — `clamp(eta * 0.5, 20, 60)` min via `computeSellZeroProgressCap`, so fast items (≤40min ETA) get the 20min floor while slow items (e.g. 114min ETA) get up to 60min, preventing long-ETA sells from being aborted at 18% of their expected duration + dynamic 75-95% ETA + <25% sold, with a **5min minimum ETA floor** so high-volume items with tiny runtime sell ETAs don't get aborted almost instantly + **progress-since-revision extension** — if the offer has made progress recently (progress increased within the last half-ETA window, tracked via `lastSellProgress`/`lastSellProgressAt` on the cache entry, updated by the stale-check loop each tick when live slot progress changes, reset to 0 on every revision/re-list/confirm) AND elapsed < 2x ETA, the ETA-based checks are skipped entirely — the offer is actively selling and gets more time instead of being prematurely revised. This prevents aborting offers that are filling at a reasonable rate but slower than the ETA predicted (e.g. Diamond dragon bolts at 67% sold when the ETA predicted 100% — the item was actively selling, not stuck). The extension is capped at 2x ETA to prevent infinitely extending truly slow items, and doesn't apply if progress stalled more than half an ETA window ago (the item is no longer actively selling). The extension does NOT affect the 0-progress absolute cap (fires at 0% progress, before the extension), the reconstructed zero-profit guard (fires regardless of progress), or the dump-floor guard (checks a hold timer before any progress checks — 90 min for rev 8 at tax break-even floor, 30 min for rev 9+ below tax break-even floor; after the hold timer expires with 0% progress, the controlled loss dump fires, pricing below the tax break-even floor at rev 9-12 to free stuck slots); buy: min(125% ETA, ETA-scaled absolute cap for 0-fill buys — `clamp(eta * 0.5, 15, 60)` for non-lowball / `clamp(eta * 0.5, 30, 90)` for lowball via `computeBuyZeroProgressCap`, so fast items keep the 15/30min floor while slow items like Ancient essence at 64min ETA get up to 60/90min before being aborted) + 0 bought, or 90% ETA + >0% but <50% bought for multi-qty (the `progress > 0` guard ensures 0-progress offers are handled only by the 0-fill check, which gives more patience — without it, a 0-progress offer with a short ETA gets aborted at 90% of ETA before the 0-fill check ever fires), or ETA-scaled no-progress for partial fills — `clamp(eta * 0.25, 10, 30)` min since progress last increased, tracked via `lastBuyProgress`/`lastBuyProgressAt` on the cache entry and updated by the stale-check loop each tick when live slot progress changes). **Buy ETA floor** (`BUY_ETA_FLOOR_MIN = 10`): runtime buy ETAs for high-volume items with small quantities (e.g. 2k Soul runes at ~3min) are mathematically correct for volume but don't account for GE queue dynamics — the offer may be queued behind other buyers at the same or higher price, and fills come in chunks, not linearly. The ETA is floored to 10 min before any stale-check threshold or break-timing computation. **Non-linear ETA model**: runtime ETAs use `eta = BASE_FILL_TIME_MIN + (qty / volume_per_hour * 60)` where `BASE_FILL_TIME_MIN = 5` — the base component represents "time to first fill" independent of quantity, acknowledging that even a small order has to wait for sellers to come along. This prevents unrealistically short ETAs for small quantities of high-volume items. The no-progress rule catches partial-fill buys that have stalled (e.g. 6/8 Occult necklaces at 74% with no movement for 15+ minutes) — aborting frees the slot and lets the partial inventory be sold. The ETA scaling gives fast items a strict 10-min floor while slow high-ticket items (e.g. 2 items with 1hr ETA) get up to 30 min of patience since long gaps between fills are normal for them. The sell ETA floor (`SELL_ETA_FLOOR_MIN = 5`) prevents rapid abort/re-list cycles on high-volume items (e.g. Ancient essence with a runtime sell ETA of 0.8min) — the mathematical ETA is correct for volume but doesn't account for the price being too high, and aborting after <1min wastes GE slots. Items removed from `merchableItems.json` are NOT immediately aborted — they may still be merchable, and the volatile list during development caused abort churn on every restart. Instead, ETA-based checks handle them using the cached `purchaseEtaMinutes` from buy time (which stores the **runtime** ETA based on the actual affordable quantity, not the simulation ETA from merchableItems.json which is based on a 50m cash stack). The stale checker prefers the cached runtime ETA over the live simulation ETA from `merchableItems.json`, falling back to the simulation ETA only if the cache has no ETA (e.g. reconstructed entries). Start an `AbortOfferFlow` if stale. Buy offers are frozen when the abort is triggered — the freeze is **global** (not account-keyed) because it represents a market/item-level signal: an item that isn't buying at the offered price on one account is unlikely to buy at that price on another account either. The freeze is NOT re-applied if the item is already frozen (e.g. a previous abort attempt failed and is being retried), and is NOT applied for config-driven aborts (item removed from list — re-buying is fine if it's added back). **Progressive freeze**: The freeze duration scales with the item's abort count (tracked in the hidden `itemAbortCountSetting`): first abort = 5 min, second = 10 min, etc., capped at 30 min. Items with effective abort count (buy + sell) ≥ 3 (`ITEM_ABORT_HARD_SKIP_THRESHOLD`) are hard-skipped entirely — the market price estimate is systematically wrong for them. Abort counts decay after 1 hour (buy) / 2 hours (sell) of no aborts. **Sell-side stale aborts**: When a sell offer is aborted as stale with <25% progress, the sell-abort count is incremented and a progressive buy freeze is applied on abort completion (deferred from detection time to avoid inflation from interrupted abort flows). The sell count feeds into the effective count (buy + sell) for the progressive freeze duration and hard-skip threshold. The item is immediately eligible for re-listing at a revised (lower) price via the existing `reviseSellPrice()` mechanism — the freeze only prevents future buys, not the current sell re-list cycle. The revision schedule progressively lowers the sell price: revisions 0–1 reduce gross profit by 5%, revisions 2–3 by 8%, revisions 4–5 by 12%, revision 6 abandons the floor (price = buyPrice − 2), revision 8 final-dumps at buyPrice − 5. This actively chases the market down until the item sells, rather than holding it in inventory at the same price and hoping the market comes back — which risks larger losses if the market continues downward. Partial-progress sells (progress > 0) are also revised, since they are legitimate "stalled near completion" aborts where the price revision is appropriate. After the abort flow completes, the cache entry is only removed if the item is NOT in inventory — if the buy partially filled during the abort flow (especially after a failed first attempt), the collected items are in inventory and the cache entry is kept to preserve buy-limit tracking. The sell scan will pick up the items in the next iteration. An abort history entry is recorded at abort completion via `recordAbort()` in `data/abort-history.ts`, capturing item, type, requested/filled qty, reason, category (`'eta'`, `'swap'`, or `'config'`), elapsed vs ETA, price, and timestamp — this is the key diagnostic for low overnight profit (aborted 0-fill buys leave no trace in merch history). **Dump-floor guard**: `isSellOfferStale` skips all stale checks when `cache.isAtDumpFloor(itemName)` returns true — i.e. the sell price is at or below the final dump floor (buyPrice − 5) AND the revision count has reached the final dump threshold (8). The price cannot be reduced any further, so aborting and re-listing at the same price just wastes bot time and resets the ETA clock. The offer is left to fill at its own pace. This catches items whose price was driven to the dump floor by an earlier bug (e.g. the reconstructed zero-profit loop) without going through the normal final-dump revision path. **Idle-activity ingredient buy protection**: when an idle activity is selected, buy offers for that activity's ingredients (e.g. volcanic ash, supercompost, chocolate bar, desert goat horn) are never aborted as stale — the user is manually buying them for the activity. The `getIdleActivityIngredientNames(bot)` dispatcher returns the lowercased ingredient name set for the selected activity, and the stale-check loop skips the abort when the buy offer's item name matches. The slot is already occupied by an active buy, so the buy scan won't try to use it for a new merch offer. **Idle-activity result product sell protection**: when an idle activity is selected, sell offers for that activity's output (e.g. goat horn dust, ultracompost, chocolate dust) are never aborted as stale — the user is manually selling the activity's output. The `getIdleActivityResultProductNames(bot)` dispatcher returns the lowercased result product name set for the selected activity, and the stale-check loop skips the abort when the sell offer's item name matches.
9. **Selling**: Find empty slot + non-coin inventory item not being bought. The inventory snapshot (`getInvSnapshot()`) **accumulates quantities across all slots with the same name** — noted stacks and unnoted singles are combined into a single total (e.g. 6 noted Warrior rings + 1 unnoted + 1 unnoted = 8 total). The `SellOfferFlow` quantity check (`sell-offer.ts`) also sums across all matching slots via `getAll()` + exact name filter, rather than relying on a single `find()` call that only returns the first slot. **Quantity handling**: When the item spans a single inventory slot, the GE already defaults to the full stack quantity — no quantity step is needed. When the item spans multiple inventory slots (e.g. a noted stack + unnoted singles in separate slots), clicking one inventory slot only selects that slot's quantity, so the flow clicks the "All" button (child slot 6 of `GE_AMOUNT_WIDGET`, opcode=57 id=1) to combine all matching slots into one offer. The `needsQtyAll` flag is set in `resolveSlot()` based on whether `matches.length > 1`. Items being SOLD in another GE slot trigger a **consolidation abort** — the existing sell is aborted (returning its items to inventory), combining with what's already there, and the next sell scan iteration places a single consolidated sell with the combined quantity. This cleans up duplicate sells that may have been created by edge cases (GE state lag, hot reloads during abort flows). Each consolidation cycle reduces the duplicate count by one. Only items with an active BUY offer in a GE slot are skipped (to avoid selling partially-filled buy collections before the buy completes). Use cached sell price (revised if re-listing) or merchableItems.json price. Pass the actual sell quantity, the item's GE buy limit, and the runtime sell ETA (computed via `computeRuntimeSellEtaMinutes` based on the actual quantity being sold) to `recordSellOffer()` for buy-limit tracking and accurate stale-check thresholds. `recordSellOffer` applies a **value-aware sell ETA cap** (`computeValueAwareSellEtaCap`) that scales with the item's total net profit: `cap = clamp(totalNetProfit * 60 / 20000, 15, 120)` — low-profit items (5k) get a 15min cap so the slot is freed sooner for better items, high-profit items (40k+) get the full 120min. This prevents low-volume, low-profit items (e.g. Goat horn: 763 qty at 10k profit, raw ETA 3442min) from occupying a slot for hours. The cap tightens automatically after revisions since re-listing at a lower price reduces total net profit. Start a `SellOfferFlow`. **Fast-sell**: Small quantities of low-value items (qty < 50 AND total sell value < 10k GP) are fast-sold at 50% of the sell price for a guaranteed quick sale to free the slot. The **net** halved price (after 2% GE tax) must still be above the buy price — if `getNetSellPrice(halvedPrice) <= buyPrice`, fast-sell is skipped and the item sells at normal price (never fast-sell at a loss after tax). **Dynamic slot freeing**: If all 8 slots are occupied with buy offers and there are sellable items in inventory, the sell scan aborts the **oldest buy offer with 0% progress** (nothing bought yet — no loss) to free a slot for the sell. This keeps slot usage dynamic: all 8 slots can be used for buys, but when a sale is needed the least-productive buy (oldest 0-progress) is sacrificed. The abort uses category `'swap'` (no buy-freeze applied).
10. **Buying**: Find empty slot + best merchable item evaluated at **runtime** based on a **per-slot budget** derived from the player's actual coins. **All 8 slots are available for buy offers** — no slots are reserved for sales. When a sell is needed, the sell scan (Step 9) dynamically frees a slot by aborting the 0-progress buy with the **lowest projected profit/hr** (oldest as tiebreaker), keeping the swap decision consistent with item selection (highest profit/hr first → sacrifice lowest profit/hr first). **Per-slot budget with profit-scaled soft cap**: The available coins are divided by the number of empty GE slots to get a `baseSlotBudget`, then multiplied by `MAX_SLOT_BUDGET_MULTIPLIER = 2.5` to get the `slotBudget` passed to the scan. This prevents a single expensive item from consuming all the cash when there are multiple empty slots to fill — with 6 empty slots and 15m coins, the budget is `min(15m, floor(15m/6) * 2.5) = 6.25m`, so a 14.8m item is skipped in favour of cheaper items that fill multiple slots. With 1 empty slot, the budget is the full coin stack (nothing else to fill). `getFirstUnoccupiedMerchableItem` returns a `BuyScanResult` containing the runtime quantity (`min(floor(slotBudget / purchasePrice), limit)`), runtime total cost, runtime profit/hr, runtime turnover ETA, runtime buy/sell ETAs (based on the actual affordable quantity, not the simulation quantity), and **profit-per-coin-per-hour** (`runtimeProfitPerSlotHour / runtimeTotalCost`). Items are ranked by **absolute profit per slot per hour** — the bot picks the highest-earning item first, then fills remaining slots with cheaper items using leftover coins. This maximises total profit across all slots. A minimum profit-per-coin-hour floor (0.005, i.e. 5k profit per 1m coins per hour) prevents wasting capital on items that earn very little per coin invested. The absolute profit/hr filter (≥ 20k) ensures cheap low-quality items aren't picked. The absolute total profit floor (≥ 20k, `RUNTIME_MIN_ABSOLUTE_PROFIT_GP`) ensures items with tiny quantities aren't picked despite high profit/hr (e.g. 1106x Death rune @ 1gp profit = 1.1k total with 0.3min ETA). The **effective volume floor** (`RUNTIME_MIN_EFFECTIVE_VOLUME = 15` units/hr) rejects items whose effective volume (min of buy/sell, after 35% market share + 15% buffer + lowball penalty) is below 15/hr — these items trade too infrequently to fill reliably and waste GE slots at 0% progress for 30+ minutes (e.g. Dark bow at 6/hr, Master wand at 3/hr, Heavy ballista at 6/hr). The ETA cap alone doesn't catch them because small GE limits keep the ETA under 120min despite terrible volume. This filters ~110 items from the pool, leaving ~92 — large enough for multi-account scaling. → ~221k/hr). Filters: profit/hr ≥ 20k, turnover ≤ 120min, total profit ≥ 20k. The runtime quantity is then adjusted for remaining GE buy limit: `min(runtimeQuantity, remaining)`. **Minimum buy offer value** (`MIN_BUY_OFFER_VALUE = 100_000` GP): After computing the adjusted total (`adjustedQty * purchasePrice`), if the total is below 100k GP, the buy offer is skipped and the bot falls through to the "nothing to do" branch — it takes a short break / logs out / rotates to the next account. This prevents wasting GE slots on tiny offers when the cash stack is low (e.g. 35 Death runes for 6.5k GP when only 6.6k coins remain). Once sells complete and coins recover above 100k, profitable offers resume. Record buy offer in cache (passing runtime buy/sell ETAs from the scan result so the cache stores accurate values for the actual offer quantity). Start a `BuyOfferFlow`. If no item passes the standard thresholds, a **partial fallback** scans with lower thresholds (profit/hr ≥ 5k, turnover ≤ 240min) to keep slots productive. If no item is found, the diagnostic logs a summary: how many items were occupied, buy-limited, frozen, unaffordable, and below threshold. **Frozen fallback**: If no non-frozen item is available, the bot falls back to a frozen item (soonest-expiring freeze preferred) rather than leaving a slot empty — an empty slot earns 0gp, while a frozen item might buy if market conditions have changed since the abort.
9. **Wait**: All slots occupied or nothing to do — idle with a humanised delay.

### GE 4-hour buy limit tracking

The GE enforces a per-item buy limit (from `merchableItems.json` `limit` field). The 4-hour window starts from the **first** item bought — not when the full limit is reached. After 4 hours from the first purchase, the limit completely resets regardless of how many were bought. For example, an item with limit 13000: buy 100 at 2:00 PM, buy 1000 more at 3:00 PM → at 6:00 PM (4 hours after first purchase) the full 13000 limit is available again.

- **Tracking**: `OfferCacheEntry` has `totalBought` (cumulative bought qty in the current window), `firstBoughtAt` (timestamp of the first purchase in the window), and `limitReachedAt` (timestamp when `totalBought >= limit`).
- **Recording**: `recordSellOffer()` in `data/offer-cache.ts` accepts `quantity` and `limit` params. The sell quantity = actual bought quantity (a buy offer may partially fill). It's added to `totalBought`; `firstBoughtAt` is set only when `totalBought` transitions from 0 to >0; when `totalBought >= limit`, `limitReachedAt` is set.
- **Checking**: `isBuyLimited(itemName)` returns true if `limitReachedAt` is set and the 4-hour window (from `firstBoughtAt`) hasn't expired. Lazily resets all tracking if the window has expired.
- **Remaining limit**: `getRemainingBuyLimit(itemName, limit)` returns `limit - totalBought` within the current window, or the full `limit` if the window has expired (resetting lazily).
- **Threshold skip**: `getBuyLimitThresholdItemNames(items, 20)` returns items where remaining < 20% of the limit. These are merged into the buy-limited set so `getFirstUnoccupiedMerchableItem()` skips them. This prevents buying tiny remaining quantities (e.g. 1280/13000 remaining).
- **Quantity adjustment**: After selecting an item to buy, the quantity is adjusted to `min(runtimeQuantity, remaining)`. The log notes when this happens: `(reduced from N — buy limit remaining)`.
- **Buying flow**: `getBuyLimitedItemNames()` returns all currently-limited item names (full limit hit + threshold-skipped). This set is passed to `getFirstUnoccupiedMerchableItem()` which skips limited items. The buy scan uses **lowball tiering**: non-lowball items (instant-fill, buy at market, `lowballPercent === 0`) are tried first, then lowball items (buy below market, `lowballPercent > 0`, slower fills, less reliable ETA). The tier order is: (1) non-lowball non-frozen, (2) non-lowball frozen fallback, (3) lowball non-frozen, (4) lowball frozen fallback, (5) partial fallback (lower thresholds: profit/hr ≥ 5k, turnover ≤ 240min). **Pre-sleep lowball priority**: during the final 30 minutes before nightly sleep (`getMinutesUntilNightlySleep(bot) ≤ 30`, exported from `antiban/session.ts`), the tier order reverses to lowball-first (tiers 1↔3, 2↔4 swap) and the lowball primary scan's turnover cap is relaxed from 120min to 240min — lowball offers are better suited for the ~4h unattended sleep window. Invalid, disabled, expired, or already-started nightly schedules do NOT activate pre-sleep mode (returns `Infinity`). The partial fallback also reverses to lowball-first during pre-sleep. **Slow Mode preferred tier**: when `autoMode === 2` (Slow) AND pre-sleep is NOT active, a tier 0 is prepended that targets lowball items with a runtime buy ETA of 30–60 minutes (`SLOW_PREFERRED_MIN_BUY_ETA_MINUTES`/`SLOW_PREFERRED_MAX_BUY_ETA_MINUTES`) using the relaxed 240min turnover cap. These slower, higher-margin fills suit the ~30-minute account login cadence. If tier 0 finds nothing, the scan falls through to the normal tier order (1–5) unchanged — fast non-lowball flips remain eligible. The frozen swap-out path (all slots occupied) also tries the slow preferred tier first when Slow Mode is active. Slow Mode does NOT alter login/logout/break/rotation/hop timing. Pre-sleep takes precedence over Slow Mode when both would apply. **All tiers enforce an absolute total profit floor** (`RUNTIME_MIN_ABSOLUTE_PROFIT_GP = 20k`): an item whose `runtimeQuantity * profitMargin < 20k` is skipped regardless of tier. This prevents placing a buy offer for a tiny quantity of an item that would earn less than 20k even if it fills perfectly — short-ETA items can show high profit/hr despite tiny absolute profit (e.g. 1106x Death rune @ 1gp profit = 1.1k total, 0.3min ETA → ~221k/hr), so the profit/hr filter alone is insufficient. The floor ensures a slot and ~30s of click time is never wasted on sub-20k offers. This ensures GE slots fill with instant-buy items before slower lowball offers are attempted, reducing slot idle time and ETA-exceeded aborts. The `lowballTier` parameter on `getFirstUnoccupiedMerchableItem` and `getFirstPartialBuyItem` controls which tier to scan (`'non-lowball'`, `'lowball'`, or `'any'`). `getFirstUnoccupiedMerchableItem` and `getFrozenFallbackItem` also accept an optional `maxTurnoverMinutes` parameter (defaults to `RUNTIME_MAX_TURNOVER_MINUTES = 120`) used by the pre-sleep lowball scan to relax to 240min.
- **Cash-stack-aware evaluation**: `determine-flips.mjs` runs at `CASH_STACK_MILLIONS = 50` to produce a wide item pool. The `CASH_STACK` acts as a **pool-width dial**: items costing more than `CASH_STACK` are filtered out, so higher values include more expensive items. The `flipScore` in the JSON is fully cash-stack-independent (`maxProfitPerSlotHour * log1p(ROI)` — no simulation-era values used), so the ranking is identical regardless of the cash stack setting. At runtime, `evaluateItemAtRuntime(item, coins)` computes the actual quantity the player can afford (`min(floor(coins / purchasePrice), limit)`), the runtime ETA (using the same volume formula as determine-flips.mjs), and the runtime profit/hr. Items are ranked by **absolute profit per slot per hour** — the bot picks the highest-earning item first, then fills remaining slots with cheaper items using leftover coins, maximising total profit across all slots. A minimum profit-per-coin-hour floor (0.005) prevents wasting capital on items that earn very little per coin invested. The `quantityToPurchase`, `totalPurchasePrice`, `purchaseEtaMinutes`, `actualProfitPerSlotHour`, and `turnoverEtaMinutes` fields in the JSON are simulation-era values (at 50m allocation) and are NOT used for runtime decisions — they're kept for diagnostic reference only.
- **Cache retention**: Cache entries are NOT removed when a sell completes. `clearSellFields()` resets `mode` to `'idle'` and clears `sellQuantity`, `partialSales`, `revisedPrices`, and `sellConfirmed`, but preserves buy-limit tracking (`totalBought`, `firstBoughtAt`, `limitReachedAt`). `recordBuyOffer()` also preserves these fields from the existing entry. The entry's mode/price fields are overwritten by the next `recordBuyOffer()`. Startup reconciliation skips entries with active buy-limit windows (totalBought > 0 within 4 hours of `firstBoughtAt`). Reconciliation also skips entries with `mode='sell'` and `sellQuantity > 0` — these have pending unrecorded sell profit that the completed-sell sweep (Step 3) must process first. Without this skip, a hot-reload between collecting a completed sell and the sweep running would permanently lose the profit (the item is no longer in any slot or inventory, so reconciliation would otherwise treat it as orphaned). The sweep clears `sellQuantity` after recording profit, so the entry becomes eligible for reconciliation on the next startup. **Pre-collect profit recording**: the sweep also records profit BEFORE the collect click when a sell slot is `completed_or_aborted` (100% progress) and the bot didn't initiate an abort — this eliminates the vulnerability window where a hot-reload between collect and the next tick's sweep could lose the profit (cache setting reverts or `fixModeMismatch` clears sell fields when a new buy is already live on the GE).
- **Post-login cleanup**: On the first auto-loop tick after logging back in from a break, `cleanupExpiredIdleEntries()` removes 'idle' entries whose buy-limit window has expired (keeping the cache bounded). Expired `buyFreezeUntil` entries are also cleaned up at this point and the global persisted freeze map is re-saved.
- **Periodic cache cleanup**: In addition to post-login cleanup, `cleanupExpiredIdleEntries()` runs every 60 seconds during long sessions without breaks (e.g. all slots occupied, no idle time to trigger a short break). This prevents expired 'idle' and buy-freeze entries from accumulating unbounded over 24/7 operation. Expired freeze entries are pruned from the global persisted setting on each cleanup. The cost is one cache iteration per 60 seconds — negligible.
- **Merch history cap & persistence**: `recordMerchCycle()` trims to the most recent 200 entries per category (profits/losses) per account, preventing unbounded growth. Merch history is persisted in a hidden JSON setting (`merchHistorySetting`, key `merchHistory`). Includes duplicate account-key migration on load: keys equivalent under whitespace + casing normalization (replaces all whitespace chars including non-breaking spaces U+00A0 with regular space, collapses multiples, trims, lowercases) are merged (profits and losses arrays concatenated, then trimmed to the cap) under a canonical key (roster match preferred, else first-seen raw key), with a normalized-lookup fallback in `getMerchHistory` for defensive casing tolerance. Write paths use the existing canonical key to prevent re-creating duplicates. Each entry now includes diagnostic fields for overnight profit analysis: `requestedBuyQty` (what the bot tried to buy vs `qty` = what actually sold), `actualBoughtQty` (from `totalBought`), `buyAbortReason` (null if buy completed naturally, or the stale reason if aborted), `buyElapsedMin`, `buyEtaMin` (original cached ETA), `revisionPrices` (array of actual sell prices at each revision, not just the count), and `sellElapsedMin` (how long the sell offer was active). These fields are optional — existing entries from before the change will have `undefined` and the log dump handles that gracefully.
- **Abort history**: Aborted offers (stale buys with 0% progress, partial-fill buys, sell aborts, frozen swap-outs) are recorded in a separate `abortHistorySetting` (hidden, key `abortHistory`) via `recordAbort()` in `data/abort-history.ts`. Includes duplicate account-key migration on load: keys equivalent under whitespace + casing normalization are merged under a canonical key (roster match preferred, else first-seen raw key), with a normalized-lookup fallback in `getAbortHistory` for defensive casing tolerance. Write paths use the existing canonical key to prevent re-creating duplicates. Each entry captures: `item`, `type` (buy/sell), `requestedQty`, `filledQty` (what actually filled before the abort — 0 for no-fill buys), `reason` (stale reason string or 'frozen swap-out'), `category` (`'eta'` for ETA-based stale aborts, `'swap'` for frozen swap-out aborts, `'config'` for legacy item-removed-from-list aborts — no longer produced but kept for existing entries), `elapsedMin`, `etaMin` (original cached ETA for comparing actual vs expected), `price`, and `date`. Capped at 200 entries per account. This is the key diagnostic for low overnight profit — aborted 0-fill buys represent wasted time and slot occupancy that merch history doesn't capture (they leave no completed cycle). The abort history is dumped alongside merch history during breaks and via the "Log Merch & Abort History" button, with the category tag shown as `[eta]`, `[swap]`, or `[unknown]` (for legacy entries without the field) before each entry.
- **Diagnostic dump helpers** (`general/dump.ts`): All cache/history/freeze dump logic is centralised in shared helpers — `dumpOfferCache`, `dumpMerchHistory`, `dumpAbortHistory`, `dumpBuyFreezes`, `dumpAllState` (calls all four), and `updateProfitDisplay` (writes the visible `profitDisplay` setting). These are used by both the auto-dump-on-logout path (`antiban/session.ts` `dumpStateOnLogout`, which also calls `updateProfitDisplay`) and the manual UI buttons (`logCacheData`, `logMerchHistory`, `logBuyFreezes` in `stark-mercher.ts`), eliminating the previous duplicated dump logic. Each cache entry line includes: `elapsed=Xmin` (minutes since `offerPlacedAt`), `net=Xgp (tax=Ygp), projProfit=±Wgp/item (±Total gp total)` (net sell price after 2% GE tax + projected profit per item and total — for sell entries only, immediately flags active sells that would be a loss after tax), `buyEta=Xmin`/`sellEta=Ymin` (cached ETAs at placement time, for comparing actual elapsed vs predicted), `confirmed=yes/no` (sell confirmation status — `no` indicates the sell flow was interrupted before the offer was placed, for diagnosing false-stale-after-restart), `partials=N batches, M sold` (partial sales summary across price revisions before the current re-list), `totalBought`, `firstBought`, `limitReached`, `sellQty`, `buyProgress=X% @ timestamp`/`sellProgress=X% @ timestamp` (last observed fill progress from the stale-check loop, for diagnosing stuck vs slowly-filling offers), `floorHits=N` (consecutive floor-hit revisions — after 2 thick-margin or 4 thin-margin, the item abandons early), and `reconstructed` (flag indicating the entry was created by reverse reconciliation after cache loss). `updateProfitDisplay` deduplicates accounts by normalized name (all whitespace chars including non-breaking spaces replaced with regular space, collapsed, trimmed, lowercased) so casing/whitespace differences between the game's `localPlayer.name` and the roster entry don't cause the same account to appear twice with different totals.

### Price revision strategy

When a sell offer doesn't sell and is re-listed (after abort + collect), the price is revised downward using an **escalating reduction** that accelerates with the number of failed revisions. This finds the market price faster instead of slowly chasing a falling market with tiny cuts. The revision only applies if the previous sell offer was confirmed on the GE (`sellConfirmed === true`) — if a hot-reload interrupted the sell flow before the offer was placed, the item is re-listed at the same price with no revision penalty.

**Escalation schedule (by revision count, 0-indexed):**

| Revisions | Reduction rate | Floor |
|-----------|---------------|-------|
| 0–1 | 10% of gross profit | tax-break-even (sell − 2% tax > buy) |
| 2–3 | 12% of gross profit | tax-break-even |
| 4–5 | 15% of gross profit | tax-break-even |
| 6 | Abandon — drop directly to floor | tax-break-even |
| 7 | 15% of remaining margin | tax-break-even |
| 8 | Final dump (drop directly to floor) | tax-break-even |

```
rate      = REVISION_RATES[min(revisionCount, 5)]  // 0.10, 0.10, 0.12, 0.12, 0.15, 0.15
floor     = taxBreakEvenFloor(buyPrice)            // uniform at every stage
reduction = max(1, floor(abs(grossProfit) * rate))
newPrice  = max(floor, currentSell - reduction)
```

- Minimum 1 gp reduction (so even thin-margin items get a nudge).
- The floor at rev 0-8 is the **tax-break-even floor** (`ceil(buyPrice / 0.98) + 1` for taxed items, `buyPrice + 1` for items below the 50gp exemption threshold) — the bot never re-lists at a guaranteed loss after 2% GE tax. This prevents the Ornate maul handle loss case where the gross margin was ~9k but the tax was ~13k, resulting in a ~4k loss, and the Redwood logs / Grimy ranarr weed loss cases where the abandon floor (`buyPrice - 2`) and final-dump floor (`buyPrice - 5`) sold below the buy price for a guaranteed loss after tax. If the market has moved below break-even, the item cycles at the floor until it sells rather than being dumped below buyPrice.
- After 6 revisions with 0% sold, the bot **abandons** — drops the sell price directly to the tax-break-even floor to free the slot faster (a percentage-based reduction would chip away slowly).
- After 8 total revisions, the bot does a **final dump** — drops the sell price directly to the tax-break-even floor to guarantee a quick sale and free the slot for a profitable item.
- **Controlled loss dump (Option 1, rev 9-12)**: After the final dump (rev 8), if the offer is still stuck at 0% progress after a 90-minute hold timer (`DUMP_FLOOR_HOLD_MIN`), the bot accepts a controlled loss by pricing **below** the tax-break-even floor. Each controlled loss revision reduces the sell price by 3% of buyPrice (min 5gp), capped at 80% of buyPrice (`CONTROLLED_LOSS_MIN_PRICE_RATIO`). Up to 4 controlled loss revisions are applied at 30-minute intervals (`DUMP_FLOOR_CONTROLLED_LOSS_HOLD_MIN`). After rev 12 or reaching the 80% minimum, the offer is left to fill at its own pace. The loss is recorded in merch history as a negative profit entry. The sell-abort count feeds into the effective count (buy + sell) for the progressive buy freeze and hard-skip.
- **Floor-hit markers**: When `computeRevisedSellPrice` returns `null` because the price is already at the tax-break-even floor, `reviseSellPrice` still advances the revision count by pushing the current price to `revisedPrices` as a "floor-hit marker". This ensures floor-stuck items (e.g. Ancient essence at buy=18, sell=19, tax-break-even floor=19) can eventually reach the abandon threshold (rev 6) and final dump (rev 8) instead of looping forever at the same price with revision count frozen at 0. The caller re-lists at the same price, but the next call to `computeRevisedSellPrice` sees the advanced count and can eventually trigger the abandon or final dump. **Dump-floor guard with controlled loss dump**: once the price reaches the tax-break-even floor and the revision count hits the final dump threshold (8), `isSellOfferStale` checks a hold timer before skipping stale checks. For rev 8, the hold is 90 min; for rev 9+, the hold is 30 min. When the hold timer expires with 0% progress, the stale checks fall through to the 0-progress absolute cap, triggering an abort + re-list at the controlled loss price (rev 9+). At rev 9+ with the price at the 80% minimum (`!canReduceControlledLoss`), the guard skips stale checks permanently — the offer is left to fill at its own pace.
- Losses are correctly tracked: `addDailyProfit` subtracts negative profit from the daily total, and `recordMerchCycle` routes negative totals into the `losses` array in merch history.
- The sale price in `merchableItems.json` does NOT include GE tax (it's `rawSalePrice - saleBufferAmount`). GE tax (2%, exempt below 50gp) is deducted at profit-tracking time in `auto-loop.ts` using `getNetSellPrice()` from `constants.ts`.

### Dynamic sell ETA abort ratio

The sell ETA abort ratio scales with profit margin so thin-margin items get more time to sell before being revised (a 1gp cut on a 2gp margin is 50% of profit), while high-margin items are revised sooner (a 5k cut on 100k is only 5%):

```
ratio = clamp(0.95 - log10(profit) * 0.075, 0.50, 0.95)
```

- 2gp margin → 93% of ETA before abort
- 50gp margin → 82% of ETA before abort
- 500gp margin → 75% of ETA before abort (matches the old fixed ratio)
- 10k margin → 65% of ETA before abort
- 100k margin → 58% of ETA before abort
- 1m+ margin → 50% of ETA before abort (capped)

The stalled-near-completion ratio (100% of ETA) remains fixed — that's about offers that are nearly done but stuck, not about price revisions.

### Sell-price fallback chain

When the auto-loop's selling flow (Step 5) needs a sell price for an inventory item, it checks sources in order:

1. **Offer cache** (`cache.getSellPrice`) — primary source. Includes price revision logic for re-listed items. Internally falls back to `merchableItems.json` if no cache entry exists.
2. **`priceHistory.json`** (`getPriceHistoryEntry`) — fallback. Written by `determine-flips.mjs` every run using the 1h average prices already fetched (no extra API calls). Contains every item from the Wiki 1h API response, not just merchable items. Used when an item is in inventory but has no cache entry and no `merchableItems.json` entry — e.g. after a long script stop, a JSON refresh during sleep, or a client reboot that lost the cache. The 1h average high price is used as the sell price; the 1h average low price is used as the buy price for profit tracking. **Freshness guard**: `isPriceHistoryFresh(entry)` checks that `fetchedAt` is within the last 10 minutes (matching the `merchableItems.json` TTL). If stale, the item is skipped and a warning is logged — `determine-flips.mjs` may have stopped running, and selling at a stale price risks listing too cheap. The item stays in inventory until fresh data arrives. **Liquidate-at-break-even**: if `getNetSellPrice(sell) <= buy` (the 1h average spread is too thin for the 2% GE tax), the item is listed at the tax-break-even price (`taxBreakEvenFloor(buy)` = `ceil(buy / 0.98) + 1` for taxed items, `buy + 1` for tax-exempt items) instead of being skipped. This frees trapped GP — the item gets listed at net-zero profit, and if it doesn't sell, the revision mechanism (rev 0-5 at break-even floor, rev 6 abandon at tax-break-even floor, rev 8 final dump at tax-break-even floor, rev 9-12 controlled loss dump below tax-break-even floor) progressively cuts the price, eventually accepting a controlled loss to free the slot. The `buyPrice` from `priceHistory` is stored in the cache entry via `recordSellOffer` so the revision logic has a floor to work from.
3. **Skip** — if neither source has a price, the item is skipped (logged in debug) to avoid selling at an unknown price.

The Wiki API fallback (`fetchWikiPrice` in `data/offer-cache.ts`) remains a stub — the `priceHistory.json` fallback now covers the use case it was intended for, without requiring a runtime API call from the plugin.

### State lifecycle for auto-loop fields

- `autoLoop: AutoLoopState` — created via `createAutoLoopState()` on the class field. Reset in `resetState()` (lifecycle.ts) via `resetAutoLoop(bot)`.
- `autoLoop.activeBuyFlow/SellFlow/AbortFlow` — set when a flow starts, cleared when it completes (done/failed). Also cleared on tick-counter reset in `onGameTick`.
- `autoLoop.cache: OfferCacheManager | null` — lazily initialised on first `autoLoopTick`. Set to `null` in `resetAutoLoop()` so it re-loads from the hidden setting on next access.
- `autoLoop.profilesInitialised` — set to `true` after delay/jitter profiles are loaded. Reset to `false` in `resetAutoLoop()`.
- `autoLoop.sellAttemptedItems/buyAttemptedItems` — cleared after each loop iteration and in `resetAutoLoop()`.
- `autoLoop.buyFreezeUntil` — persisted in the hidden `buyFreezeSetting` (key `buyFreeze`, default `'{}'`, `hidden: true`). **Global (not account-keyed)** — a flat map of lowercase item name → freeze-until timestamp (ms). Freezes represent a market/item-level signal (an item isn't buying at the offered price), which is independent of which account is active. With multi-account rotation, an account-keyed freeze would let account B immediately re-buy an item that account A just aborted as stale. Set in three scenarios: (1) when a stale **buy** offer is aborted — progressive freeze of 5 min × min(effectiveCount, 6) → 5/10/15/20/25/30 min, where effectiveCount = buy abort count + sell abort count; items with 3+ effective aborts are hard-skipped entirely; (2) when a stale **sell** offer is aborted with <25% progress — same progressive freeze based on the effective count, applied on abort completion (deferred from detection time to avoid inflation from interrupted abort flows); (3) **loss-history cooldown** — on startup/account switch, scans merch history `losses` for entries within `LOSS_HISTORY_LOOKBACK_MS` (6h). For each item with a recent loss, applies a buy freeze until `latestLossTime + LOSS_COOLDOWN_FREEZE_MS` (2h). Multiple recent losses for the same item extend the freeze by taking the latest loss timestamp. This prevents re-buying items that have been confirmed unprofitable (e.g. Amethyst dart, Dragonstone bolts (e)). Sell aborts feed into the same protection as buy aborts via the effective count — an item that consistently fails to sell at the projected price has a systematically wrong price estimate, just as a buy that consistently fails to fill. `occupiedNames` already prevents re-buying while the item is being sold. Abort-history seeding still runs on startup/account switch (scanning sell aborts within 24h) to seed the `sellCount`, which feeds into the effective count for hard-skip. The freeze does NOT prevent the current sell re-list cycle (the sell scan doesn't check `buyFreezeUntil`) — it only prevents future buys. **Not re-applied if the item is already frozen** (buy abort path) — if a previous abort attempt failed and the bot retries the abort, the existing freeze timer is preserved instead of being extended. The sell-abort path extends the freeze if the new sell-based freeze is later than the existing one (e.g. a buy freeze from a previous cycle). **Not applied for config-driven aborts** (item removed from `merchableItems.json`) — the item wasn't stale, just removed from the list, so re-buying is fine if it's added back. Restored in `resetAutoLoop()` on script start via `loadBuyFreeze()` (expired entries dropped during load; legacy nested `{ account: { item: until } }` format is migrated to flat on first load, keeping the latest expiration per item). Saved on every freeze set and on every cleanup that prunes expired entries (post-login, periodic 60s, buy-scan lazy). Survives hot reloads so a freeze applied after aborting a stale offer is not lost on plugin toggle. **Frozen items are skipped during buy scans, but used as a fallback** when no other merchable items are available — an empty slot earns 0gp, while a frozen item might buy if the price issue has resolved. The fallback is tiered by lowball: non-lowball frozen items are tried before lowball frozen items (via `getFrozenFallbackItem` with the `lowballTier` parameter), and logs which frozen item is being used. **Swap-out**: when all slots are occupied and a buy slot has a frozen item with < 50% progress, the bot checks if a non-frozen merchable item is now available. If so, it aborts the frozen item's buy offer (without re-freezing — the item is already frozen) to make room for the non-frozen item. Offers at >= 50% progress are left to finish naturally.
- `autoLoop.failureCounters` — `Record<string, number>` mapping failure key (`geOpen`, `geSubScreen`, `collect`) to consecutive failure count. Incremented by `recordFailure()`, reset to 0 by `resetFailure()` on success, cleared entirely in `resetAutoLoop()` and when the post-login settle completes. See "Consecutive failure termination" section.
- `autoLoop.buyFreezeSources` — in-memory `Map<string, string>` (lowercase item name → source label) tracking why each item was frozen. Labels: `'buy-abort'`, `'sell-abort'`, `'loss-cooldown'`. Diagnostic only — not persisted. Cleared in `resetAutoLoop()`; repopulated as freezes are applied. After a reload, sources are unavailable and the dump shows `'restored'`. Used by `dumpBuyFreezes` and the buy-scan frozen-items log to distinguish freeze types.
- `autoLoop.historicalProtectionsApplied` — `Set<string>` of normalized account names (trimmed + lowercased) for which historical protections (loss-history cooldown + abort-history seeding) have been applied this session. Prevents re-applying on every tick. Cleared in `resetAutoLoop()` so protections re-apply after a reload (idempotent via count reconciliation in `applyHistoricalProtections`).
- `autoLoop.abortSlotInfo` — set when an abort flow is initiated (stale offer or frozen swap-out). Carries `{ type, itemName, progress, reason, category, etaMin, requestedQty, price, placedAt, countSellAbort }` for abort history recording and deferred sell-abort count + freeze tracking. The `category` field (`'eta'`, `'swap'`, or `'config'`) tags the abort reason for diagnostic filtering. The `countSellAbort` flag is set `true` at stale-detection time when a sell offer with `<25%` progress is aborted for a non-config reason; the actual `incrementItemSellAbortCount` + progressive buy freeze run on abort **completion** (`flow.status === 'done'`), guarded by this flag — so a reload interrupting the abort flow does not inflate the count or apply a freeze (the in-memory `abortSlotInfo` is lost, the count is not incremented, and the next stale detection creates a fresh flag). The sell count feeds into the effective count (buy + sell) for the progressive freeze duration and hard-skip threshold. Cleared (`null`) when the abort flow ends (done or failed) and in `resetAutoLoop()`. The extended fields (reason, category, etaMin, requestedQty, price, placedAt) are captured from the cache entry and GE slot at abort trigger time so the abort history entry can be recorded at abort completion.
- `autoLoop.pendingReprices` — in-memory `Map<string, number>` (lowercase item name → bumped buy price). Set when a high-profit stalled buy qualifies for repricing instead of freezing (profit/hr > 100k, gross margin ≥ 10gp, reprice count < 2, post-bump profit/hr ≥ 50k). After the abort completes, the buy scan checks this map and overrides the purchase price. Cleared when the buy is placed, when the item is frozen (normal abort), when the item is swapped out, and in `resetAutoLoop()`. In-memory only — not persisted. If the bot reloads mid-reprice, the reprice is lost and the item gets a normal buy at the original price (safe fallback).
- `autoLoop.buyRepriceCounts` — in-memory `Map<string, number>` (lowercase item name → reprice count). Caps reprices at `BUY_REPRICE_MAX_COUNT` (2). Reset when a buy is successfully placed (the reprice worked) or when the item is frozen (normal abort — fresh start after freeze expires). Cleared in `resetAutoLoop()`. In-memory only.

### GE booth object detection

`findGeBooth()` in `grand_exchange/clerk.ts` searches for tile objects within 20 tiles with `nameContains('Grand Exchange')` and `hasAction('Exchange')`. `findExchangePoint()` returns the nearest of clerk NPC or booth object. `openGe()` interacts with whichever is closer. This satisfies the requirement to check for the "Exchange Grand Exchange Booth" object as the first automated operation.

### Consecutive failure termination

Major "stuck" states terminate the bot after 3 consecutive failures (`MAX_CONSECUTIVE_FAILURES` in `auto-loop.ts`). Recoverable failures (price mismatch, quantity validation, search not found) do NOT use this system — they press Esc and retry the loop.

Tracked operations:
- **`geOpen`** — GE cannot be opened or no clerk/booth found. Counter increments on each failed attempt, resets when `isGeOpen()` returns true.
- **`geSubScreen`** — GE sub-screen (offer config / search / price prompt) cannot be closed with Escape. Counter increments on each Escape attempt, resets when no sub-screen is detected.
- **`collect`** — Completed/aborted offer cannot be collected. Counter increments when collect click fails, resets when no completed/aborted slots remain.

On the 3rd consecutive failure, `bot.terminated = true` and `bot.terminationReason` is set with a clear message. Counters are stored in `autoLoop.failureCounters` (a `Record<string, number>`), reset in `resetAutoLoop()` and when the post-login settle completes.

### Cash-allocation implementation

The iterative, turnover-aware allocation is implemented in `determine-flips.mjs`:

1. **First pass**: for every candidate item, compute `actualProfitPerSlotHour` at the base allocation (`max(AVERAGE_SLOT_CASH_STACK_ALLOCATION, purchasePrice)`).
2. **Average baseline**: compute `averageActualProfitPerSlotHour` across all candidates.
3. **Scale**: for each item, scale the base allocation by `sqrt(actualProfit / averageProfit)` (dampened; only above-average items scale up).
4. **Turnover cap**: using the ETA from the scaled quantity, apply:
   - `turnoverEtaMinutes < 30` → max 80% of `CASH_STACK`
   - `30 <= turnoverEtaMinutes < 90` → max 50% of `CASH_STACK`
   - `turnoverEtaMinutes >= 90` → max 25% of `CASH_STACK`
5. **Iterate**: repeat allocation → quantity → ETA → cap until `cashAllocation` stabilises (up to 5 iterations), then compute final quantity, ETAs, and profitability.

This also fixes two underlying problems:
- **Volume double-counting removed**: `calculateSlotCashAllocation` no longer multiplies by `threeHourAverageHourlyVolume` after `maxProfitPerSlotHour` already includes volume.
- **Scaling uses actual profit per slot hour**: `actualProfitPerSlotHour` (post-ETA) is used instead of `maxProfitPerSlotHour` (pre-ETA), so slow, expensive items are not over-allocated.

### Design intent for flip selection

- Primary objective: **maximum profit per hour**.
- `AVERAGE_SLOT_CASH_STACK_ALLOCATION_RATIO` (0.125 = 1.25m of 10m) is the *base* per-slot allocation.
- Scaling above the base is allowed only for items that are both **very profitable AND high turnover**.
- Target ~8 active slots (all GE slots used for buys; sells dynamically free slots by aborting oldest 0-progress buys).
- Allocation must be **iterative and turnover-aware** because ETA depends on quantity and quantity depends on allocation.
- Confirmed turnover caps:
  - `< 30 min` → max 80% of stack
  - `30–90 min` → max 50% of stack
  - `> 90 min` → max 25% of stack

### Spike and drop protection (`determine-flips.mjs`)

The flip-selection pipeline applies four layers of price-spike/drop protection. Each layer is a separate filter function; an item must pass all four to enter the merchable pool.

1. **5m-vs-1h transient clamp** (purchase and sale): `determineFiveMinuteVsOneHourPurchasePriceChange` / `determineFiveMinuteVsOneHourSalePriceChange`. If the 5-minute volume is ≥ 5% of the 1-hour volume (i.e. the 5m sample is representative), and the 5m price exceeds a margin-aware threshold (`clamp(marginPct * 0.4, 2%, 5%)` for buys, `clamp(marginPct * 0.4, 2%, 10%)` for sells) above the 1h average, the 5m price is **clamped** to the threshold — not rejected. Downward movements are kept (favourable for buys, conservative for sells). This catches transient 5-minute spikes without discarding the item.

2. **Sustained sale-price spike filter** (1h/3h vs 7d): `determineSalePriceSpike`. Rejects an item if the 1h or 3h average sale price is significantly above the 7-day average sale price. Margin-aware thresholds:
   - 1h: `clamp(marginPct * 0.5, 10%, 20%)`
   - 3h: `clamp(marginPct * 0.4, 8%, 15%)`
   This prevents selling into a sustained uptrend where the sell price is likely to revert.

3. **Sustained purchase-price spike filter** (1h/3h vs 7d): `determinePurchasePriceSpike`. Mirrors the sale-side filter but for the buy price. Rejects an item if the 1h or 3h average buy price is significantly above the 7-day average buy price. Margin-aware thresholds (higher than the sell-side filter):
   - 1h: `clamp(marginPct * 0.5, 15%, 25%)`
   - 3h: `clamp(marginPct * 0.4, 12%, 20%)`
   This catches genuine manipulation/transient pump spikes (e.g. Ham robe at 69.83%, Dark kebbit fur at 22.10%, Antipoison(3) at 18.24%) while allowing normal market fluctuation (5-10% moves) to pass through. The higher minimum thresholds (vs 10%/8% on the sell side) reflect empirical analysis: normal market trends regularly produce 5-10% moves above the 7-day average that are legitimate and profitable (e.g. Twinflame staff at 7.41% spike sold for +78,581gp profit), and zero losses in merch history were caused by purchase-price spikes — all losses were sell-side (price drops during holding, thin margins + GE tax).

4. **Sustained purchase-price drop filter** (1h/3h vs 7d): `determinePurchasePriceDrop`. Rejects an item if the 1h or 3h average buy price is significantly **below** the 7-day average buy price (`oneHourPurchasePrice < 7dAvg * 0.92` or `threeHourAvg < 7dAvg * 0.90`). This prevents buying into a sustained downtrend (crash) where the price is likely to continue falling.

The 5m-vs-1h clamp is the first line of defense against transient spikes; the 1h/3h-vs-7d filters are the second line against sustained trends. An item can pass the 5m clamp (because the 1h price itself is elevated) but be caught by the sustained spike filter if the spike is large enough to indicate manipulation rather than normal market movement.

## Daily profit tracking

Profit is tracked per-account in a hidden JSON setting (`dailyProfitSetting`, key `dailyProfit`). Each account has a `{ dayStartedAt, profit }` entry.

- **Recording**: Profit is recorded at two points, using `sellQuantity` stored in the offer cache entry. Both points deduct GE tax (2%, exempt below 50gp) using `getNetSellPrice()` from `constants.ts`:
  1. **Re-list time (Step 5)**: When an item is re-listed after an abort, `soldQty = entry.sellQuantity - item.quantity` (the difference between what was listed and what's still in inventory = what actually sold). Profit = `(getNetSellPrice(entry.sellPrice) - entry.buyPrice) * soldQty`. This handles partial aborts accurately.
  2. **Completed-sell sweep (Step 3)**: Runs every tick at the top of Step 3. A fast-path check (`cache.hasActiveSellEntries()`) skips the entire sweep when no cache entries have `mode='sell'` with `sellQuantity > 0`, avoiding per-tick inventory scans when no sells are in flight. When active sell entries exist, for each such entry, checks if the item is in any GE slot or inventory. If neither, the sell completed 100% (post-collect path) — profit = `(getNetSellPrice(entry.sellPrice) - entry.buyPrice) * entry.sellQuantity`. Clears `sellQuantity` to prevent double-counting. **Pre-collect path**: if the matching slot is `completed_or_aborted` (100% progress) and type=sell, and the bot did NOT initiate an abort (no `activeAbortFlow`, no `abortSlotInfo`), and the entry is not reconstructed and is sell-confirmed, the profit is recorded IMMEDIATELY — before the collect click. This prevents profit loss when a hot-reload occurs between the collect and the next tick's sweep (the cache setting may revert to a stale pre-sell state, or `fixModeMismatch` may clear sell fields when a new buy for the same item is already live on the GE). Reconstructed entries are excluded from the pre-collect path (can't distinguish natural completion from an interrupted abort from a previous session).
- **Merch history**: When a cycle completes (100% sold), `recordMerchCycle` is called with `totalProfit = (getNetSellPrice(avgSold) - entry.buyPrice) * totalQty`. The `avgSold` field in the history entry is the pre-tax average sell price (for reference); the `profit` field is after tax. The entry also includes diagnostic fields: `requestedBuyQty`/`actualBoughtQty` (from `totalBought`), `buyAbortReason` (null for natural completion), `buyEtaMin` (from `purchaseEtaMinutes`), `revisionPrices` (full array from `entry.revisedPrices`), and `sellElapsedMin` (time from `offerPlacedAt` to now).
- **`sellQuantity` field**: Stored in `OfferCacheEntry` when `recordSellOffer` is called. Represents the quantity currently listed in an active sell offer. Cleared by `clearSellQuantity()` after profit is recorded.
- **`sellConfirmed` field**: Set to `false` by `recordSellOffer()` when the sell flow starts, then set to `true` by `confirmSellOffer()` after the `SellOfferFlow` completes successfully. If a hot-reload interrupts the sell flow before the offer is placed on the GE, `sellConfirmed` remains `false`. The re-list logic checks `isSellConfirmed()` before calling `reviseSellPrice()` — if unconfirmed, the item is re-listed at the same price with no revision penalty (the offer never had a chance to sell). Backward compat: `undefined` (existing entries from before this field) is treated as `true`. Cleared by `clearSellFields()`.
- **Hot-reload write ordering (prevents double-counting)**: The completed-sell sweep captures the profit data from the cache entry, mutates the cache (clear sell fields), and calls `cache.save()` BEFORE calling `addDailyProfit()` or `recordMerchCycle()`. This ensures that if a hot-reload occurs between the cache save and the profit write, the cache already reflects the cleared sell state — the sweep won't re-trigger. The worst case is losing one tracking entry (the actual GP is still correct in the coin pouch), never double-counting. The re-list partial sell path records partial sale batches in the cache via `cache.recordPartialSale(...)` but does NOT call `addDailyProfit()` — partial profit is only counted once, at completed-cycle time, via `recordCompletedSellProfit()` which computes the total weighted profit across all partial batches. This prevents the double-counting that occurred when partial profit was recorded at re-list time and again at completion.
- **Day rollover**: `getDayStartMs(now)` returns the epoch ms of midnight (00:00) for the current UK-local day. On every read (`getDailyProfit`) and write (`addDailyProfit`), the stored `dayStartedAt` is compared to the current day's midnight. If they differ, the profit is reset for the new day. This handles the script being stopped before midnight and restarted the next day.
- **Persistence**: The state is saved to the visible setting on every `addDailyProfit` call. It survives both hot-reloads and client restarts.
- **Per-account**: Keyed by `currentPlayerName` (or `localPlayer.name` as fallback), same as the offer cache.
- **GE tax**: The `salePrice` from `merchableItems.json` does NOT include GE tax (it's `rawSalePrice - saleBufferAmount`). GE tax is deducted at profit-tracking time using `getNetSellPrice(sellPrice)` from `constants.ts` (2% tax, exempt for items below 50gp). This ensures the daily profit and merch history reflect actual realized profit after tax.

## World hopping

The bot hops to a random safe world matching the current mode (members world for Normal/Slow, F2P world for F2P mode) at a profile-scheduled interval (18–45 min base, with jitter and long-tail outliers). This is adapted from stark-mixology's hopper.

### Settings

- `hopWorlds` (boolean, default `true`) — enables/disables world hopping.
- `hopRegion` (combo, default `0` = Any) — restricts hops to UK, Germany, US, or Any.
- `resetHop` (button) — clears the scheduled next hop timer.
- `forceHop` (button) — forces the next hop to become due immediately (still waits for a safe boundary).

### Hop profile (`HoppingProfile` in `SessionProfile`)

- `minMinutes` / `maxMinutes` — base interval range (18–25 / 32–45 min).
- `jitterMinutes` — +/- jitter (3–6 min).
- `outlierChance` / `outlierMultiplier` — long-tail outlier (3–8% chance, 1.3–1.8x).
- `outlierNestedChance` / `outlierNestedMultiplier` — nested outlier (15–25% chance, 1.3–1.5x).
- `cooldownMinTicks` / `cooldownMaxTicks` — post-hop cooldown (20–35 / 35–55 ticks).
- `resumeMinMs` / `resumeMaxMs` — post-hop resume delay (2500–5000 / 5000–8000 ms).

### Safe boundary

The only blockers for a hop are:
1. `hopInProgress` — a hop is already in flight.
2. `!isPlayerIdle(bot)` — the player is animating or moving.
3. Idle buffer — player has been idle for less than 2 ticks.

GE interface, inventory items, and location all persist across hops or are transient.

### Hop flow

1. `scheduleNextHop` samples a bimodal/burst interval (70% normal 15–60 min, 20% burst 2–8 min, 10% long 60–150 min) and sets `nextHopAtMs`. After a burst hop, the next interval has a 50% chance of also being a burst. The hop timer is **global** (not per-account) — it is shared across account rotations since only one account is active at a time. The timer is persisted to the hidden `hopState` setting via `saveHopState` so script reloads don't reset the schedule.
2. When `Date.now() >= nextHopAtMs`, `forceHopPending` is set to pause new actions.
3. `isAtSafeBoundary` is checked — waits for player to be idle AND every GE flow (`activeBuyFlow`/`activeSellFlow`/`activeAbortFlow`) to be null with the auto-loop phase at `idle` or `waiting`. The hop stays pending until all flows have fully ended.
4. `pickWorld` filters `titan.state.world.list()` for safe worlds matching the current mode (members for Normal/Slow, F2P for F2P mode) in the chosen region.
5. `titan.state.world.hopIngame(worldId)` dispatches the hop.
6. `completeHop` (called from `onGameStateChanged` / `hopStep`) waits for login + world match, then resets state, resets `inventoryOpenEnsured = false`, and starts a resume delay.
7. After the resume delay, the inventory-open guard runs (closes lingering world switcher, clicks inventory tab), then the auto-loop resumes normally.

### State lifecycle

- All hop fields are reset in `resetHopState` (called from `resetState` in lifecycle.ts). After the reset, `loadHopState` restores the persisted global hop timer from the hidden `hopState` setting if it is still in the future.
- `resetInFlightActionState` (called by `completeHop`) clears auto-loop flows, test flows, idle-for-break flags, and marks cache reconciliation and post-login cleanup for re-run after the transition.
- `sessionPlayStartMs` is set to -1 when a nightly break starts, and lazily re-initialised when the player is logged in and not on a break.

## Overlay HUD (minimal)

The overlay was stripped to the absolute minimum: one rect + two text lines showing the current autoMode label (Paused / Normal / Slow / F2P) and the script start time ("Start: HH:MM"). All previous fields (Status, TIMERS, Session (Day), Next Hop, Sleep Time, Wake Time, Next Account, Inventory Coins, Daily Profit, Delay, Fatigue) were removed to eliminate per-frame allocations and native handle accumulation from the render path. The render callback does zero allocations, zero `Date.now()`, zero native SDK reads — it reads only `bot.overlayStatusText` and `bot.sessionStartUKTime` (plain-JS strings updated in `onEnable` / `onDisable` / `onSettingChanged`). The start time is derived from `bot.scriptStartMs` (persisted via the hidden `scriptStartSetting` — hot-reload only), so it survives hot reloads, resets on full client restart, and resets on `terminate()`.
